## The core idea in one line

**A table stores facts about a *row*. A knowledge graph stores facts *between*
things — and that difference is not a convenience, it is the difference between
a question being answerable and being impossible.**

---

## 1. The shape all your data has had so far

Every dataset in Chapters 1–11 looked like this:

```
  student_id      cgpa   backlogs   attendance   branch
  ─────────────────────────────────────────────────────
  CB.EN.U4CSE45   7.84      0          71.5       CSE
  CB.EN.U4CSE46   8.90      1          88.0       CSE
  CB.EN.U4ECE12   6.50      0          92.0       ECE
```

**One row per thing. One column per property.** Linear regression, decision
trees, the neural network, the placement engine — every model you have built
consumes exactly this shape. It is so universal that it is easy to forget it is
a *choice* rather than the nature of data.

Now the same shape, holding clinical data:

```
  patient_id   age   egfr   drug_1      drug_2     drug_3       gene_1
  ──────────────────────────────────────────────────────────────────────
  P001         72    45     Warfarin    Aspirin    Metformin    VKORC1
```

It fits. Technically nothing is wrong. Then a real clinical question arrives:

> *"Warfarin and Aspirin both raise bleeding risk. Warfarin's effect is
> modulated by the VKORC1 gene. This patient carries a VKORC1 variant. Is the
> risk compounded?"*

---

## 2. Why the table cannot answer it

The instinct is "the table can't represent relationships." True, but too vague —
a table represents one kind of relationship perfectly well: **between a row and
its own values.** Row P001 relates to `age=72`. That is exactly what a table is
for.

What it cannot hold is a fact that belongs to *two entities at once*:

```
  drug_1      drug_2
  ─────────────────────
  Warfarin    Aspirin
     │           │
     └─────?─────┘
           ▲
           └── the fact that these two INTERACT is nowhere in the table.
               They are two strings sitting in adjacent cells.
```

Being in the same row means *both belong to the same patient*. It says nothing
about how they relate to **each other**.

And there is nowhere to put that fact. "Warfarin interacts with Aspirin" is not
a property of P001 — it is true for the pair, for every patient on both drugs,
and for patients who don't exist yet.

`VKORC1` has the same problem. The table records that P001 carries it. That
VKORC1 *modulates Warfarin metabolism* is a fact about a gene and a drug,
belonging to no patient at all.

> **A table can only store facts about a row. It has nowhere to put facts that
> exist *between* two entities.**

---

## 3. Trying to force it — three failures

The obvious fix is to add columns:

```
  patient_id  drug_1  drug_2  d1_interacts_d2  d1_modulated_by  ...
```

### Failure 1 — column explosion

Every *pair* of drugs needs its own column. The count is `n(n−1)/2` — the same
`itertools.combinations` arithmetic from 11.5, now as table structure.

**Verified:**

```
   drugs | pairs needed | note
  ----------------------------------------------
       3 |            3 |
       4 |            6 |
       5 |           10 |
      10 |           45 |
      20 |          190 |
      57 |         1596 |
     100 |         4950 | ← exceeds Postgres' ~1600 column limit
```

A patient on 100 medications is unusual but not impossible in ICU or oncology.
And since the drug count varies per patient, you would need the widest possible
table for the rarest possible patient, with almost every cell empty.

### Failure 2 — rigidity

Adding a fourth drug means `ALTER TABLE` — a **schema migration on a live
clinical database**, to record something as ordinary as a new prescription.

### Failure 3 — duplication, and the drift it becomes

Warfarin+Aspirin is dangerous for everybody. Stored per patient, that single
fact is copied into 10,000 rows.

**Drift** = copies of one fact that were identical when written, but stop
agreeing after someone updates some and misses others.

**Verified simulation** — DrugBank v5.2 downgrades the severity, and the update
script touches 9,847 of 10,000 rows before timing out:

```
  before update: 1 distinct value(s) -> {'HIGH'}
  after partial update (9847 rows touched):
    distinct values now: ['HIGH', 'MODERATE']
    P0001 says MODERATE, P9999 says HIGH
    -> the database now contradicts itself. No error was raised.
```

Ask "how dangerous is Warfarin+Aspirin?" and the answer now depends on which
patient you happen to ask through. No error, no warning — two answers to one
question and no way to tell which is current.

> **Duplicated data does not stay duplicated. It stays *almost* duplicated,
> which is worse than either being right or being obviously wrong.**

### Failure 4 — it still cannot answer the question

Even with every column, the clinical question needs three facts chained:

```
  Warfarin ──interacts_with──► Aspirin
  Warfarin ──metabolised_by──► VKORC1
  P001     ──has_variant────► VKORC1
```

Three facts about three different *pairs* of things. **No arrangement of columns
on a patient table holds them, because not one of them is a fact about the
patient.**

---

## 4. The graph

Turn the entities into **nodes** and the facts into **labelled edges**:

```
                    ┌─────────────┐
                    │   VKORC1    │  (Gene)
                    └─────────────┘
                       ▲        ▲
          metabolised_by│        │has_variant
                       │        │
   ┌──────────┐        │        │        ┌──────────┐
   │ Warfarin │────────┘        └────────│   P001   │
   │  (Drug)  │                          │(Patient) │
   └──────────┘                          └──────────┘
        │                                      │
        │ interacts_with                       │ takes
        │ {severity: HIGH,                     │
        │  source: DrugBank v5.1}              ▼
        ▼                                 ┌──────────┐
   ┌──────────┐                           │ Aspirin  │
   │ Aspirin  │◄──────────────────────────│  (Drug)  │
   └──────────┘                           └──────────┘
```

### Vocabulary

| Term | Meaning | Example |
|---|---|---|
| **Node** | a thing | `Warfarin`, `P001`, `VKORC1` |
| **Label** | what *kind* of thing | `:Drug`, `:Patient`, `:Gene` |
| **Edge** (relationship) | a fact linking two nodes | `INTERACTS_WITH` |
| **Property** | a key-value on a node *or* an edge | `severity: "HIGH"` |
| **Hop** | traversing one edge | `P001 → Warfarin` is one hop |

**Verified — the same facts, stored once:**

```
  nodes: 4   edges: 5
    (Warfarin) -[INTERACTS_WITH]-> (Aspirin)  {'severity': 'HIGH', 'source': 'DrugBank v5.1'}
    (Warfarin) -[METABOLISED_BY]-> (VKORC1)
    (P001)     -[HAS_VARIANT]->    (VKORC1)   {'variant': 'rs9923231'}
    (P001)     -[TAKES]->          (Warfarin)
    (P001)     -[TAKES]->          (Aspirin)
```

### The three failures, fixed

| Table failure | Graph answer |
|---|---|
| column explosion | a new drug is **one new edge**, not a new column |
| rigidity | no schema migration — edges are data, not structure |
| duplication → drift | the interaction is **one edge**, shared by every patient |

And notice where `severity` and `source` live — **on the edge**. Those are the
`Alert` fields from Chapter 11.2. The rule engine does not invent them; it reads
them off the relationship it just traversed.

---

## 5. Tracing the clinical question by hand

### ❌ The wrong mental model: one long chain

The natural first guess is a single walk outward:

```
  P001 ──takes──► Warfarin ──interacts_with──► Aspirin ──?──► VKORC1
                                                          ▲
                                                          └── this edge does not exist
```

**Verified:**

```
  Aspirin -METABOLISED_BY->  []   <- empty: the chain DEAD-ENDS
```

Aspirin has no relationship to VKORC1. You cannot reach the gene by continuing
forward from the interaction.

### ✅ The right model: three walks, and a convergence

Starting at P001 is correct as a *query strategy* — that is exactly how you would
write it. The correction is about the **shape of what you find**:

```
                         VKORC1
                        ▲      ▲
          has_variant  ╱        ╲  metabolised_by
                      ╱          ╲
                  P001            Warfarin
                     │                │
                     └───takes────────┘
                     │
                     └───takes────► Aspirin
                                       ▲
                                       │ interacts_with
                                    Warfarin
```

**Verified traversal:**

```
  walk 1: P001 -TAKES-> ['Warfarin', 'Aspirin']
  walk 2: which of those pairs INTERACT? [('Warfarin', 'Aspirin')]
  walk 3a: P001 -HAS_VARIANT-> ['VKORC1']
  walk 3b: Warfarin -METABOLISED_BY-> ['VKORC1']
  CONVERGENCE: ['VKORC1']  <- reached from BOTH patient and drug
```

**The convergence is the finding.** VKORC1 arrives from two independent
directions — once from the patient, once from the drug — and that is what makes
this variant clinically relevant *to this drug*. A variant in some unrelated
gene would still be one hop from P001, but nothing would link it to Warfarin, so
nothing would fire.

> **You traverse from one starting point, but the thing you are matching is a
> *shape*, not a line.** Cypher matches shapes — that is 12.5.

**Both paths are 2 hops.** That number matters: two hops is the shortest journey
a table fundamentally cannot make.

### ⚠️ The graph does not conclude anything

A tempting phrasing is "then the graph identifies the amplification." It does
not. The graph holds facts:

- an interaction exists
- a gene metabolises a drug
- a patient carries a variant

Concluding *"therefore the risk is amplified"* is a **rule** — Chapter 11.2 —
reading those facts.

```
  Neo4j            supplies the FACTS       (stored, curated, never learned)
  decision_engine  draws the CONCLUSION     (a rule, with evidence and source)
```

Keep that boundary sharp. It is the 11.3 distinction: **a knowledge graph is a
knowledge base, not a reasoner.**

---

## 6. Direction — a first look

The edge is stored one way:

```
  (Warfarin) -[INTERACTS_WITH]-> (Aspirin)
```

But the fact is symmetric — Warfarin and Aspirin interact with *each other*.
Neo4j has no undirected edge; every edge points somewhere.

**Verified:**

```
  directed   query Aspirin->Warfarin : False   <- MISSES IT
  undirected query Aspirin -Warfarin : True    <- finds it
  directed   query Warfarin->VKORC1  : True    <- correct
  directed   query VKORC1->Warfarin  : False   <- correctly false
```

Two different relationships, two different treatments:

```
  INTERACTS_WITH   symmetric   → query WITHOUT direction    -[r]-
  METABOLISED_BY   asymmetric  → query WITH direction       -[r]->
```

Reversing `METABOLISED_BY` would claim the enzyme is metabolised by the drug,
which is false. Full treatment in 12.2.

## 7. Runnable file

```python
"""12.1 — why a table cannot hold a two-hop clinical question,
   and what a graph does instead. Requires: pip install networkx"""

import itertools
import networkx as nx

# ── the table approach, priced out ────────────────────────────
print("drugs -> interaction columns needed")
for n in [3, 5, 10, 57, 100]:
    print(f"  {n:>4} -> {n*(n-1)//2:>5}")

# ── drift: one fact stored 10,000 times ───────────────────────
rows = {f"P{i:04d}": "HIGH" for i in range(1, 10001)}
for i, pid in enumerate(rows):
    if i >= 9847:                       # the update script times out
        break
    rows[pid] = "MODERATE"
print(f"\ndistinct severities now: {sorted(set(rows.values()))}  <- contradiction")

# ── the graph ─────────────────────────────────────────────────
G = nx.MultiDiGraph()
G.add_edge("Warfarin", "Aspirin", key="INTERACTS_WITH",
           severity="HIGH", source="DrugBank v5.1")
G.add_edge("Warfarin", "VKORC1", key="METABOLISED_BY")
G.add_edge("P001", "VKORC1", key="HAS_VARIANT", variant="rs9923231")
G.add_edge("P001", "Warfarin", key="TAKES")
G.add_edge("P001", "Aspirin", key="TAKES")


def out(node, rel):
    """One hop outward along a named relationship."""
    return [v for u, v, k in G.out_edges(node, keys=True) if k == rel]


def linked(a, b, rel):
    """Undirected match — the edge counts either way round."""
    return G.has_edge(a, b, rel) or G.has_edge(b, a, rel)


# ── the traversal ─────────────────────────────────────────────
drugs = out("P001", "TAKES")
interacting = [(a, b) for a, b in itertools.combinations(drugs, 2)
               if linked(a, b, "INTERACTS_WITH")]
variants = out("P001", "HAS_VARIANT")

print(f"\npatient takes      : {drugs}")
print(f"interacting pairs  : {interacting}")
print(f"patient variants   : {variants}")

for drug, _ in interacting:
    genes = out(drug, "METABOLISED_BY")
    convergence = set(genes) & set(variants)
    print(f"{drug} metabolised by {genes} -> convergence: {sorted(convergence)}")

print(f"\nAspirin -METABOLISED_BY-> {out('Aspirin','METABOLISED_BY')}"
      "   <- the single-chain model dead-ends here")
```

## 8. Never forget

1. **A table stores facts about a row.** It has nowhere to put a fact that
   belongs to two entities jointly. That is the whole reason graphs exist.

2. **Forcing pairwise facts into columns costs `n(n−1)/2`** and still cannot
   answer a two-hop question, no matter how many columns you add.

3. **Duplication becomes drift.** 10,000 copies of a fact do not stay identical;
   they become *almost* identical, silently, with no error.

4. **Relationships are first-class in a graph.** An edge has a type *and*
   properties — `severity`, `evidence`, `source`. Chapter 11's alert fields live
   on the edge.

5. **The fact is stored once and shared.** Update one edge, every patient sees
   the change. This is the structural cure for drift.

6. **A traversal is a shape, not a line.** The Warfarin/VKORC1 finding comes
   from two independent 2-hop paths *converging* on one node — not from one long
   chain. Chains dead-end.

7. **The graph stores; the rule concludes.** Neo4j never says "risk amplified."
   It says these edges exist. `decision_engine.py` makes the claim, and cites the
   edge. (Ch 11.2 / 11.3.)

8. **Direction is a query-time question.** Symmetric facts (`INTERACTS_WITH`)
   are matched without direction; asymmetric ones (`METABOLISED_BY`) must keep
   it, or the query asserts something false.
