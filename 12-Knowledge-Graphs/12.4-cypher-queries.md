>
> **Reading this cold?** You need two things. From 12.1: a graph has **nodes**
> (things), **edges** (facts linking two things) and **properties** (key-value
> data on either). From 12.3: Cypher draws patterns — `()` is a node, `[]` a
> relationship, `-->` direction, `{}` properties, `:` a label or type.

---

## The core idea in one line

**Every variable in a pattern must be constrained by something, or Cypher will
happily match the entire database — and in a clinical system that is a screen
full of false alarms.**

---

## 1. The three clauses

```cypher
MATCH  (d:Drug {name: "Warfarin"})-[r:INTERACTS_WITH]-(other:Drug)
WHERE  r.severity = "HIGH"
RETURN other.name, r.severity, r.source
```

```
  MATCH   ──►  draw the shape you're looking for
  WHERE   ──►  filter what the shape found
  RETURN  ──►  choose which parts to hand back
```

**Note the syntax is identical to writing.** In 12.3 you wrote
`CREATE (w:Drug {...})-[:INTERACTS_WITH]->(a:Drug {...})`; here you read with
the same drawing. That is unusual — SQL uses completely different syntax for
`INSERT` and `SELECT`. In Cypher, the pattern *is* the query language.

Two carried-forward details:

- `-[r:INTERACTS_WITH]-` has **no arrowhead** — 12.2 established interactions
  are symmetric, so match either direction.
- `r` is a variable on the **relationship**, needed because `RETURN` refers back
  to `r.severity`.

---

## 2. `WHERE` versus a filter in the pattern

The same query, written two ways:

```cypher
-- version A: filter in WHERE
MATCH (d:Drug {name: "Warfarin"})-[r:INTERACTS_WITH]-(other:Drug)
WHERE r.severity = "HIGH"
RETURN other.name

-- version B: filter in the pattern
MATCH (d:Drug {name: "Warfarin"})-[r:INTERACTS_WITH {severity: "HIGH"}]-(other:Drug)
RETURN other.name
```

**Verified — identical results:**

```
  version A (WHERE r.severity = 'HIGH')   : 3 rows
  version B (pattern {severity:'HIGH'})   : 3 rows
  identical: True
```

### ❌ "Use WHERE when you need more conditions"

Not the distinction. You can stack several inside the braces:

```cypher
MATCH (d:Drug)-[r:INTERACTS_WITH {severity: "HIGH", source: "DrugBank v5.1"}]-(other)
```

Two conditions, both in the pattern, works fine. **Quantity is not the limit.**

### ✅ The real limit: braces test equality, and nothing else

`{severity: "HIGH"}` is an equality test. That is the entire vocabulary of the
braces. Anything else has nowhere to go but `WHERE`:

```cypher
WHERE r.confidence > 0.8                     -- comparison
WHERE d.name STARTS WITH "War"               -- string matching
WHERE r.severity IN ["HIGH", "CRITICAL"]     -- membership
WHERE d.approved_year < 2000                 -- range
WHERE other.name <> d.name                   -- comparing two VARIABLES
WHERE NOT (d)-[:CONTRAINDICATED_IN]->(:Disease {name: "CKD"})   -- absence
```

**Verified:**

```
  WHERE r.confidence > 0.8               -> 3 rows
  WHERE r.severity IN ['HIGH','CRIT']    -> 3 rows
  WHERE r.source STARTS WITH 'Drug'      -> 4 rows
```

The fifth line above matters more than it looks. **Braces compare a property to
a literal. `WHERE` can compare a property to another *variable* in the query** —
one node against another. That is a different class of expression, not an
extension of the same one.

> **Put equality filters in the pattern; everything else in `WHERE`.** Pattern
> filters read better and let the query planner narrow the search earlier.

## 3. The unconstrained-variable bug

Here is the clinical question from 12.1: *find every interaction among the drugs
a patient is taking.*

```cypher
MATCH (p:Patient {id: "P001"})-[:TAKES]->(a:Drug)-[r:INTERACTS_WITH]-(b:Drug)
RETURN a.name, b.name, r.severity
```

It looks right. It is wrong in **two** distinct ways.

### Bug 1 — mirrored pairs

The undirected `-[r]-` matches from both ends, so the same edge is found twice:

```
  a=Warfarin, b=Aspirin,  HIGH
  a=Aspirin,  b=Warfarin, HIGH     ← same edge, reported twice
```

One clinical fact, two alerts on screen. Annoying, visible, easily fixed.

### Bug 2 — nothing constrains `b`

```cypher
MATCH (p:Patient {id: "P001"})-[:TAKES]->(a:Drug)-[r:INTERACTS_WITH]-(b:Drug)
       └──────── p is pinned ────────┘   └─ a is       └─ b is ONLY
                                            reached       required to
                                            via TAKES     be a :Drug
```

**`b` is any drug in the entire database that interacts with `a`.** Nothing
connects it back to the patient. Warfarin interacts with hundreds of drugs in
DrugBank, and every one of them matches.

**Verified** — P001 has prescriptions for Amiodarone, Aspirin, Metformin,
Warfarin:

```
  BUGGY: MATCH (p)-[:TAKES]->(a)-[r:INTERACTS_WITH]-(b:Drug)
    a=Amiodarone   b=Warfarin     HIGH
    a=Amiodarone   b=Simvastatin  HIGH      <- patient NOT on this drug
    a=Aspirin      b=Warfarin     HIGH
    a=Warfarin     b=Aspirin      HIGH
    a=Warfarin     b=Amiodarone   HIGH
    a=Warfarin     b=Fluconazole  MODERATE  <- patient NOT on this drug
  6 rows returned
    mirrored duplicate pairs : 2
    FALSE ALARMS (b not taken): 2
```

Six rows for what should be two facts. Two of them warn about **Simvastatin and
Fluconazole — drugs the patient has never been prescribed.**

That is not noise. It is **false alarms in a safety system**, and alert fatigue
is a documented cause of real clinical harm: clinicians who see irrelevant
warnings learn to dismiss all warnings, including the true ones.

### ✅ The fix

```cypher
MATCH (p:Patient {id: "P001"})-[:TAKES]->(a:Drug)-[r:INTERACTS_WITH]-(b:Drug)
WHERE (p)-[:TAKES]->(b)          -- b must ALSO be one of the patient's drugs
  AND a.name < b.name            -- and report each pair once
RETURN a.name, b.name, r.severity
```

**Verified:**

```
  FIXED: WHERE (p)-[:TAKES]->(b) AND a.name < b.name
    a=Amiodarone   b=Warfarin     HIGH
    a=Aspirin      b=Warfarin     HIGH
  2 rows returned
```

Six rows down to two. Both bugs gone.

### Pattern-as-boolean

```cypher
WHERE (p)-[:TAKES]->(b)
```

This is a **pattern used as a truth value** — *"does this shape exist?"* It has
no SQL equivalent. And `WHERE NOT (...)` tests for absence:

```cypher
WHERE NOT (p)-[:HAS_ALLERGY]->(:Allergen)<-[:CONTAINS]-(b)
```

### ⚠️ `a.name < b.name` is NOT 12.2's rejected scheme

12.2 rejected alphabetical ordering as a way to **store** edges. This looks
similar and is a different thing entirely:

```
  12.2 rejected:  store edges alphabetically     ← a convention, unenforceable,
                                                    fails silently when bypassed
  12.4 accepts:   filter results alphabetically  ← runs on rows MATCH already found
```

The query-time filter depends on nothing about how the edge was written. It
cannot drift, because there is no stored invariant to drift from.

## 4. The real `ddi_rule` query — reified and active-only

12.2 established that a prescription must be a **node**, not a flat edge,
because a patient can take the same drug more than once over time:

```
   (P001:Patient) ──HAS_PRESCRIPTION──► (Rx:Prescription) ──FOR_DRUG──► (Warfarin:Drug)
                                             │
                                             └── dose_mg, started, ended, status
```

Reaching a drug is now **two hops**:

```cypher
-- old, flat
(p:Patient)-[:TAKES]->(a:Drug)

-- new, reified
(p:Patient)-[:HAS_PRESCRIPTION]->(rx:Prescription)-[:FOR_DRUG]->(a:Drug)
```

### ❌ The condition that no longer works

```cypher
AND (p)-[:TAKES]->(b)
```

There is no `TAKES` edge in this schema. This pattern matches nothing and the
query returns zero rows.

### ❌ Two hops, but still wrong

```cypher
AND (p)-[:HAS_PRESCRIPTION]->(:Prescription)-[:FOR_DRUG]->(b)
```

Correct shape, wrong semantics. It says *"the patient has **some** prescription
for b"* — **including a discontinued one.** A drug stopped in March would still
fire an interaction alert today.

### ✅ The correct query

```cypher
MATCH (p:Patient {id: "P001"})-[:HAS_PRESCRIPTION]->(rxa:Prescription)-[:FOR_DRUG]->(a:Drug),
      (p)-[:HAS_PRESCRIPTION]->(rxb:Prescription)-[:FOR_DRUG]->(b:Drug),
      (a)-[r:INTERACTS_WITH]-(b)
WHERE rxa.status = "ACTIVE"
  AND rxb.status = "ACTIVE"
  AND a.name < b.name
RETURN a.name, b.name, r.severity, r.evidence, r.source,
       rxa.dose_mg AS dose_a, rxb.dose_mg AS dose_b
```

```
        ┌── rxa (ACTIVE) ──► a ──┐
   p ──►│                        │ INTERACTS_WITH
        └── rxb (ACTIVE) ──► b ──┘
```

Three patterns separated by **commas**, sharing the variables `p`, `a` and `b` —
Cypher joins them on the shared names. Two *separate* prescription variables,
`rxa` and `rxb`, because they are different prescriptions and each needs its own
status check.

### Why the condition had to move from `WHERE` into `MATCH`

A pattern-as-boolean in `WHERE` can only answer *"does this shape exist?"* —
true or false. **It cannot hand you a variable.** Since `rxb.status` is needed,
the pattern must be *matched*, not merely tested.

> **Test only → pattern in `WHERE`. Need a value from it → pattern in `MATCH`.**

### Verified — the payoff

```
  Rx001  Warfarin         5mg  DISCONTINUED
  Rx002  Warfarin       2.5mg  ACTIVE
  Rx003  Aspirin         75mg  ACTIVE
  Rx004  Metformin      500mg  ACTIVE
  Rx005  Amiodarone     200mg  DISCONTINUED

  flat  TAKES  -> ['Amiodarone', 'Aspirin', 'Metformin', 'Warfarin']
  ACTIVE only  -> ['Aspirin', 'Metformin', 'Warfarin']

  final query rows:
    Aspirin (75mg) + Warfarin (2.5mg) -> HIGH
```

**One row. The correct one.** And note the dose reported is 2.5mg — the *current*
prescription, not the 5mg course that ended in March. A flat `TAKES` edge could
not have told them apart.

**What the status filter removed:**

```
  Rx001 Warfarin (stopped 2026-03-20) would have paired with ['Amiodarone', 'Aspirin']
  Rx005 Amiodarone (stopped 2026-02-15) would have paired with ['Warfarin']
```

Amiodarone was discontinued in February. Without the status filter it fires a
HIGH-severity interaction against Warfarin — for a drug the patient stopped
taking six months ago.

### The three stages of the fix

```
  naive query                        6 rows   (2 mirrored, 2 false alarms)
  + constrain b to the patient       2 rows   (correct set of drugs)
  + require ACTIVE prescriptions     1 row    (correct set of CURRENT drugs)
```

Each stage removes a specific class of error, and each error was silent.

## 5. Query reference

```cypher
-- one node
MATCH (d:Drug {drugbank_id: "DB00682"}) RETURN d

-- optional match: keep the row even when the pattern is absent
MATCH (d:Drug {name: "Warfarin"})
OPTIONAL MATCH (d)-[:CONTRAINDICATED_IN]->(dis:Disease)
RETURN d.name, dis.name            -- dis is null when there is none

-- counting and grouping
MATCH (d:Drug)-[r:INTERACTS_WITH]-(other)
RETURN d.name, count(r) AS n
ORDER BY n DESC LIMIT 10

-- collecting into a list
MATCH (p:Patient {id:"P001"})-[:HAS_PRESCRIPTION]->(rx)-[:FOR_DRUG]->(d)
WHERE rx.status = "ACTIVE"
RETURN p.id, collect(d.name) AS current_drugs

-- absence
MATCH (d:Drug)
WHERE NOT (d)-[:INTERACTS_WITH]-()
RETURN d.name                      -- drugs with no known interactions

-- parameters: ALWAYS use these, never string-concatenate
MATCH (d:Drug {drugbank_id: $drug_id}) RETURN d
```

> **Always pass values as parameters (`$drug_id`), never by building the query
> string.** Concatenation is a Cypher-injection vulnerability, and parameterised
> queries let Neo4j cache the execution plan.

## 6. Runnable file

```python
"""12.4 — the three stages of fixing the DDI query.
   Simulates Cypher semantics; no database required."""

from itertools import product

INTERACTIONS = [
    ("Warfarin",   "Aspirin",     {"severity": "HIGH",     "confidence": 0.95}),
    ("Warfarin",   "Amiodarone",  {"severity": "HIGH",     "confidence": 0.91}),
    ("Warfarin",   "Fluconazole", {"severity": "MODERATE", "confidence": 0.78}),
    ("Amiodarone", "Simvastatin", {"severity": "HIGH",     "confidence": 0.88}),
]

DRUGS = ["Warfarin", "Aspirin", "Metformin",
         "Amiodarone", "Fluconazole", "Simvastatin"]

PRESCRIPTIONS = [
    {"id": "Rx001", "drug": "Warfarin",   "dose_mg": 5,   "status": "DISCONTINUED"},
    {"id": "Rx002", "drug": "Warfarin",   "dose_mg": 2.5, "status": "ACTIVE"},
    {"id": "Rx003", "drug": "Aspirin",    "dose_mg": 75,  "status": "ACTIVE"},
    {"id": "Rx004", "drug": "Metformin",  "dose_mg": 500, "status": "ACTIVE"},
    {"id": "Rx005", "drug": "Amiodarone", "dose_mg": 200, "status": "DISCONTINUED"},
]


def interacts(a, b):
    """Undirected match:  -[r:INTERACTS_WITH]-"""
    for x, y, props in INTERACTIONS:
        if {a, b} == {x, y}:
            return props
    return None


ever_taken = sorted({r["drug"] for r in PRESCRIPTIONS})
active_rx = [r for r in PRESCRIPTIONS if r["status"] == "ACTIVE"]

# ── stage 1: nothing constrains b ────────────────────────────────
naive = [(a, b, p["severity"])
         for a in ever_taken for b in DRUGS
         if (p := interacts(a, b))]
print(f"naive                    -> {len(naive)} rows")
for a, b, s in naive:
    flag = "" if b in ever_taken else "   <- FALSE ALARM"
    print(f"    {a:12} {b:12} {s}{flag}")

# ── stage 2: constrain b to the patient, one row per pair ────────
constrained = [(a, b, p["severity"])
               for a in ever_taken for b in ever_taken
               if a < b and (p := interacts(a, b))]
print(f"\n+ b constrained, a<b     -> {len(constrained)} rows")
for a, b, s in constrained:
    print(f"    {a:12} {b:12} {s}")

# ── stage 3: only ACTIVE prescriptions ───────────────────────────
final = [(rxa["drug"], rxb["drug"], p["severity"],
          rxa["dose_mg"], rxb["dose_mg"])
         for rxa, rxb in product(active_rx, repeat=2)
         if rxa["drug"] < rxb["drug"] and (p := interacts(rxa["drug"], rxb["drug"]))]
print(f"\n+ ACTIVE only            -> {len(final)} rows")
for a, b, s, da, db in final:
    print(f"    {a} ({da}mg) + {b} ({db}mg) -> {s}")
```

## 7. Never forget

1. **Cypher reads with the same syntax it writes with.** The pattern is the
   query language, unlike SQL's separate `INSERT`/`SELECT` grammars.

2. **Braces test equality only.** ❌ Not "WHERE is for more conditions" — you can
   stack several in the braces. Comparison, ranges, `IN`, `STARTS WITH` and
   absence all require `WHERE`.

3. **`WHERE` can compare two variables; braces cannot.** `other.name <> d.name`
   has no pattern equivalent. That is a different class of expression.

4. **Every variable in a pattern must be constrained by something.** An
   unconstrained `(b:Drug)` matches every drug in the database — hundreds of
   false alarms with no error.

5. **False alarms are a safety failure, not a cosmetic one.** Alert fatigue
   teaches clinicians to dismiss warnings, including true ones.

6. **Undirected `-[r]-` finds each edge from both ends.** Filter with
   `a.name < b.name` to report each pair once.

7. **Query-time ordering is not 12.2's rejected storage convention.** One runs
   on rows already matched and cannot drift; the other was an unenforceable
   invariant about how edges are written.

8. **Pattern-as-boolean in `WHERE` answers "does this exist?" and returns no
   variable.** If you need a value from the pattern — `rxb.status` — it must be
   matched in `MATCH`.

9. **Commas in `MATCH` join patterns on shared variable names.** Two
   prescriptions need two variables, `rxa` and `rxb`.

10. **Reification pays off here.** `status = "ACTIVE"` is what stops a drug
    discontinued in March from firing an alert today — and it also reports the
    *current* 2.5mg dose rather than the old 5mg one.

11. **Always parameterise (`$drug_id`).** String concatenation is an injection
    vulnerability and defeats plan caching.
