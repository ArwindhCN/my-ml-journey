## The core idea in one line

**Every design decision here reduces to one question: does anything need to be
said *about* this thing, or found *from* it?**

---

## 1. The question schema design answers

12.1 gave you nodes and edges. Now the harder problem: for any given fact, what
should be a node, what should be an edge, and what should be a property?

Get it wrong and every query you write later fights the structure. Worse, some
questions become unanswerable — not slow, but genuinely impossible without
rebuilding the graph.

Three decisions, in order of how often they bite:

```
  1. NODE or PROPERTY?          the most common call
  2. WHICH DIRECTION?           the most silently dangerous
  3. EDGE or REIFIED NODE?      the one that bites hardest later
```

---

## 2. Decision one — node or property?

The fact to place: **Warfarin is metabolised by the CYP2C9 enzyme, which is
encoded by the CYP2C9 gene.**

```
  DESIGN A — enzyme as a property on the edge
  ───────────────────────────────────────────
   (Warfarin:Drug) ──METABOLISED_BY {enzyme: "CYP2C9"}──► (CYP2C9:Gene)


  DESIGN B — enzyme as its own node
  ─────────────────────────────────
   (Warfarin:Drug) ──METABOLISED_BY──► (CYP2C9:Enzyme) ──ENCODED_BY──► (CYP2C9:Gene)
```

Both store the same information. Both answer *"what metabolises Warfarin?"*

### ❌ The wrong reason to prefer B: "A would be messier"

**Design A is the tidier graph.** Fewer nodes, fewer edges, less to draw. B adds
an entire node type and an extra hop for every drug. If neatness were the
criterion, **A wins**.

So neatness cannot be the test.

### ✅ The right test: ask a question *about the enzyme*

*"Which other drugs are metabolised by CYP2C9?"* — a real clinical question,
because two drugs competing for one enzyme is itself an interaction mechanism.

**Verified:**

```
  DESIGN A (property):
    scanning ALL 3 edges comparing strings...
    exact-match on 'CYP2C9' -> ['Warfarin']
    MISSED: ['Phenytoin', 'Ibuprofen']  <- same enzyme, different spelling

  DESIGN B (node):
    ask the node for its incoming edges -> ['Ibuprofen', 'Phenytoin', 'Warfarin']
    no scan, no string comparison, no drift possible
```

The test data held `"CYP2C9"`, `"cyp2c9"` and `"CYP-2C9"` — the same enzyme,
entered three ways over three years by three people. As a string property they
are three unrelated values. As a node it exists **once**, and every drug points
at that one node.

```
  DESIGN B                                DESIGN A
  ────────                                ────────
        (CYP2C9:Enzyme)                    Warfarin ─{enzyme:"CYP2C9"}─►
        ▲     ▲     ▲                      Phenytoin ─{enzyme:"cyp2c9"}─►
        │     │     │                      Ibuprofen ─{enzyme:"CYP-2C9"}─►
  Warfarin Phenytoin Ibuprofen                        ▲
                                              a string copied onto
   one node. Ask it for its                   unrelated edges.
   incoming edges — answered.                 Nothing connects them.
```

Two things are wrong with A, and both matter:

**It requires a scan.** Finding the other drugs means examining *every*
`METABOLISED_BY` edge in the database and comparing text. That is a full table
scan — inside a graph database, which exists precisely to avoid them.

**It re-introduces drift** (12.1). Three spellings are three different enzymes
as far as the database is concerned. Nothing will ever tell you.

### The rule

> **Does anything need to be said *about* this thing, or found *from* it?
> → node. Does it only describe the relationship it sits on? → property.**

Applied to fields you already know from Chapter 11:

| | Node or property? | Why |
|---|---|---|
| `CYP2C9` | **node** | other drugs connect to it; it has its own properties |
| `severity: "HIGH"` | **property** | describes this one interaction and nothing else |
| `confidence: 0.87` | **property** | belongs to this edge alone |
| `DrugBank v5.1` | **node**, arguably | many edges cite it; you may want its version, date, licence |

`source_database` sits right on the boundary. As a string it is fine — until you
want *"show me everything sourced from DrugBank v5.0 so I can re-verify it after
the v5.1 release."* Then it must be a node. That tension is what **12.6
(provenance)** is about.

## 3. Decision two — which direction?

```
   (Warfarin:Drug) ──INTERACTS_WITH──► (Aspirin:Drug)
```

Warfarin and Aspirin interact with *each other*. The relationship is
**symmetric** — there is no sense in which Warfarin is the "from" and Aspirin
the "to". But **Neo4j has no undirected edge.** Every edge points somewhere. You
must store a direction whether or not one exists in reality.

Three strategies:

```
  1.  store one edge, arbitrary direction, ignore direction when querying
  2.  store two edges, one each way
  3.  store one edge, always written from the alphabetically-first drug
```

### ❌ Option 2 — two edges

Every fact stored twice. This is 12.1's duplication problem, reintroduced
deliberately. Update the severity on one and forget the other, and the database
says HIGH in one direction and MODERATE in the other. Which is true? Neo4j will
happily create both and never mention the disagreement.

### ❌ Option 3 — alphabetical ordering

This is the one that looks clever, and it deserves a careful treatment because
the obvious objection to it is **wrong**.

**The obvious objection:** "different scripts will sort differently." That is
not right. Sorting is deterministic. If both the writer and the reader call the
same `canonical()` function, they produce the same key, every time.

**Verified — while every write goes through the helper, option 3 works
perfectly:**

```
  store (all writes went through the helper): [('Aspirin', 'Warfarin')]
    query Warfarin/Aspirin       opt1=True  opt3=True
    query aspirin/WARFARIN       opt1=True  opt3=True
```

**The real failure is a write that never went through the helper at all:**

```
                    ┌──────────────────┐
   ingest_ddi.py ──►│                  │  ← uses canonical_merge()  ✓
   admin console ──►│      Neo4j       │  ← a raw MERGE             ✗
   partner import ─►│                  │  ← someone else's script   ✗
   a colleague's ──►│                  │  ← a quick fix at 1am      ✗
   quick fix        └──────────────────┘
                            ▲
                   accepts every one of them.
                   Has no opinion about direction.
```

**Verified — one raw MERGE stores `(Warfarin)→(Ibuprofen)`, violating the
alphabetical rule:**

```
  store now: [('Aspirin', 'Warfarin'), ('Warfarin', 'Ibuprofen')]
                                             opt1    opt3
    query Ibuprofen/Warfarin                 True   False  <-- MISSED
    query Warfarin/Ibuprofen                 True   False  <-- MISSED
```

Option 3 finds **nothing** for a real, stored interaction. No exception, no
warning — the clinician simply sees no alert. That is precisely the Chapter 11
failure mode: a `200 OK` with an empty list, indistinguishable from "these drugs
are safe together."

### Why the database cannot enforce the rule

Neo4j enforces constraints it understands:

```cypher
CREATE CONSTRAINT FOR (d:Drug) REQUIRE d.name IS UNIQUE       -- ✓ understands "unique"
CREATE CONSTRAINT FOR (d:Drug) REQUIRE d.name IS NOT NULL     -- ✓ understands "not null"
```

Now try to express *"an INTERACTS_WITH edge must point from the
alphabetically-first drug name to the second"*:

```cypher
CREATE CONSTRAINT ... REQUIRE ???
```

There is no such constraint — in Neo4j or any other graph database. The rule
compares a property on the *start* node against a property on the *end* node and
asserts an ordering between them. Nothing offers that.

So the rule can live only in application code, which means:

```
  A CONSTRAINT is enforced by the database   → holds no matter who writes.
  A CONVENTION is enforced by discipline     → holds until someone doesn't know.
```

This is the "correctness depends on human memory" failure from 11.1, in a new
costume.

### ✅ Option 1 — store one edge, query undirected

```cypher
MATCH (a:Drug {name: $drug_a})-[r:INTERACTS_WITH]-(b:Drug {name: $drug_b})
RETURN r.severity, r.evidence, r.source
```

Look closely at `-[r:INTERACTS_WITH]-` — **no arrowhead**. That is Cypher for
"traverse this edge in either direction."

```
  -[r]->    DIRECTED     follows the arrow only
  -[r]-     UNDIRECTED   follows it either way      ← use for symmetric facts
```

Compare what each design requires to be correct:

```
  OPTION 3     a shared canonical() function
               + every writer uses it
               + every reader uses it
               + nobody ever writes a raw MERGE
               + the function never changes behaviour
               ────────────────────────────────────
               = correct

  OPTION 1     -[r:INTERACTS_WITH]-
               ────────────────────────────────────
               = correct
```

> **When two designs are both correct, prefer the one with fewer things that
> must stay true.** Option 1 cannot drift, because there is no invariant to
> drift from.

### But direction often *is* the fact

```
  (Warfarin)-[:INTERACTS_WITH]-(Aspirin)      symmetric  → query undirected
  (Warfarin)-[:METABOLISED_BY]->(CYP2C9)      asymmetric → the arrow IS the fact
  (Drug)-[:CONTRAINDICATED_IN]->(Disease)     asymmetric → direction carries meaning
```

`METABOLISED_BY` reversed would claim the enzyme is metabolised by the drug —
false. Query that one **directed, always**. Getting it backwards produces
answers that are confidently wrong rather than empty, which by the 11.1 standard
is worse.

> **Direction is a property of the *relationship*, not of the storage.** Store it
> once however it arrived; decide at query time whether direction means
> anything. Never invent a direction just to have one.

## 4. Decision three — when an edge is not enough

Back to the patient. In 12.1 the edge was simply `P001 —takes→ Warfarin`. But a
patient does not merely take a drug — they take it *at a dose*, *from a date*,
*prescribed by someone*, and they may have taken it before and stopped.

```
   (P001:Patient) ──TAKES {dose_mg: 5, started: "2026-01-15"}──► (Warfarin:Drug)
```

Now the real history: **5mg from January, stopped in March, restarted at 2.5mg
in June.**

There is **one** edge between those two nodes, and it holds **one** set of
properties. Three attempts, three failures:

```
  attempt 1: overwrite the properties
             {dose_mg: 2.5, started: "2026-06-01"}
             → the January–March course is GONE. History erased, silently.

  attempt 2: add numbered property names
             {dose_mg: 5, started: "...", ended: "...",
              dose_mg_2: 2.5, started_2: "..."}
             → 12.1's column explosion, now on an edge.
               A third course needs dose_mg_3. A fourth needs dose_mg_4.

  attempt 3: create a second TAKES edge between the same two nodes
             → Neo4j allows it, but "is P001 on Warfarin?" now returns two
               edges and you must inspect both to find which is current.
               Every query downstream gets harder.
```

**Verified — attempt 1, the silent history loss:**

```
  January course : {'dose_mg': 5, 'started': '2026-01-15'}
  after June restart (overwrite): {'dose_mg': 2.5, 'started': '2026-06-01'}
  -> the January-March course is GONE. No error raised.
```

### ✅ The fix: reification

All three fail for one reason. **A prescription is not a property of the
patient-drug pair. It is an event with its own identity** — its own dates, dose,
prescriber, and reason for stopping. It is a *thing*, and things are nodes.

```
                    ┌──────────────────────────────┐
   (P001:Patient)──►│ (Rx001:Prescription)         │──►(Warfarin:Drug)
        │           │  dose_mg: 5                  │
        │           │  started: 2026-01-15         │
        │           │  ended:   2026-03-20         │
        │           │  status:  DISCONTINUED       │
        │           └──────────────────────────────┘
        │
        │           ┌──────────────────────────────┐
        └──────────►│ (Rx002:Prescription)         │──►(Warfarin:Drug)
                    │  dose_mg: 2.5                │
                    │  started: 2026-06-01         │
                    │  status:  ACTIVE             │
                    └──────────────────────────────┘
```

**Reification** = turning a relationship into a node so it can have its own
identity and properties.

**Verified:**

```
    (Rx001) dose=5mg    2026-01-15 -> 2026-03-20  [DISCONTINUED]
    (Rx002) dose=2.5mg  2026-06-01 -> None        [ACTIVE]

  'what is P001 currently taking?' -> filter status=ACTIVE -> ['Rx002']
```

### The payoff is immediate

`ddi_rule` (Ch 11.2) should only check drugs the patient is **currently** taking.
A Warfarin course discontinued in March must not fire a bleeding-risk alert
today. With a flat `TAKES` edge that question is unanswerable. With prescription
nodes it is a filter on `status: ACTIVE`.

> **When a relationship needs its own properties that change over time, or when
> there can be more than one of it between the same two things, it is not an
> edge. It is a node.**

Note this is the *same test* as CYP2C9, arriving from a different direction. If
you need to say things **about** the relationship, it deserves node status.

## 5. Runnable file

```python
"""12.2 — the three schema decisions, demonstrated.
   Requires: pip install networkx"""

import networkx as nx

# ══ DECISION 1 — node or property? ══════════════════════════════
print("Q: which other drugs are metabolised by CYP2C9?\n")

# Design A: enzyme as a string property. Real-world spelling drift included.
edges_A = [("Warfarin",  {"enzyme": "CYP2C9"}),
           ("Phenytoin", {"enzyme": "cyp2c9"}),
           ("Ibuprofen", {"enzyme": "CYP-2C9"})]
found = [d for d, p in edges_A if p["enzyme"] == "CYP2C9"]
print(f"  A (property): scan every edge, match strings -> {found}")
print(f"                missed {[d for d,p in edges_A if p['enzyme']!='CYP2C9']}")

# Design B: enzyme as a node.
B = nx.MultiDiGraph()
for drug in ["Warfarin", "Phenytoin", "Ibuprofen"]:
    B.add_edge(drug, "CYP2C9", key="METABOLISED_BY")
users = [u for u, v, k in B.in_edges("CYP2C9", keys=True)
         if k == "METABOLISED_BY"]
print(f"  B (node):     ask the node for incoming edges -> {sorted(users)}")


# ══ DECISION 2 — direction ══════════════════════════════════════
def canonical(name):
    return name.strip().lower()

def undirected(a, b, store):
    """Option 1: match on the SET of endpoints. No ordering rule exists."""
    return any({canonical(a), canonical(b)} == {canonical(x), canonical(y)}
               for x, y in store)

def ordered(a, b, store):
    """Option 3: requires every edge to be stored alphabetically."""
    return tuple(sorted([canonical(a), canonical(b)])) in \
           [(canonical(x), canonical(y)) for x, y in store]

store = [("Aspirin", "Warfarin")]          # written via the helper: a before w
print(f"\nall writes via helper -> undirected={undirected('Warfarin','Aspirin',store)}"
      f"  ordered={ordered('Warfarin','Aspirin',store)}")

store.append(("Warfarin", "Ibuprofen"))    # a raw MERGE. Violates the convention.
print(f"one raw MERGE added  -> undirected={undirected('Ibuprofen','Warfarin',store)}"
      f"  ordered={ordered('Ibuprofen','Warfarin',store)}   <- silently missed")


# ══ DECISION 3 — reification ════════════════════════════════════
edge = {"dose_mg": 5, "started": "2026-01-15"}
edge = {"dose_mg": 2.5, "started": "2026-06-01"}     # the June restart
print(f"\nflat edge after restart: {edge}   <- January course erased")

R = nx.MultiDiGraph()
R.add_node("Rx001", dose_mg=5,   started="2026-01-15",
           ended="2026-03-20", status="DISCONTINUED")
R.add_node("Rx002", dose_mg=2.5, started="2026-06-01",
           ended=None, status="ACTIVE")
for rx in ["Rx001", "Rx002"]:
    R.add_edge("P001", rx, key="HAS_PRESCRIPTION")
    R.add_edge(rx, "Warfarin", key="FOR_DRUG")

active = [n for n, d in R.nodes(data=True) if d.get("status") == "ACTIVE"]
print(f"reified: both courses kept; currently active -> {active}")
```

## 6. Never forget

1. **Node or property? Ask whether anything is said *about* it or found *from*
   it.** Not whether the diagram looks tidy — the property version is usually
   the tidier one and still the wrong call.

2. **A repeated string property is a scan waiting to happen**, and a drift
   waiting to happen. As a node it exists once and every user points at it.

3. **Neo4j has no undirected edge.** You must store a direction even for a
   symmetric fact; decide at *query time* whether it means anything.

4. **`-[r]-` traverses either way; `-[r]->` follows the arrow.** One character,
   and it is the difference between finding an interaction and missing it.

5. **A constraint is enforced by the database; a convention is enforced by
   discipline.** No graph database can express "edges must be stored
   alphabetically," so that rule holds only until a write bypasses your helper.

6. **Prefer the design with fewer things that must stay true.** When two are
   both correct, the one requiring no maintained invariant wins.

7. **A silent failure loses to a visible one, always.** A wrongly-directed edge
   is a valid edge — the query just returns nothing, which reads as "safe."

8. **Direction is sometimes the fact itself.** `METABOLISED_BY` reversed is
   false. Symmetric → undirected; asymmetric → keep the arrow. Never invent a
   direction just to have one.

9. **When a relationship needs its own changing properties, or can occur more
   than once between the same two nodes, reify it into a node.** Two Warfarin
   courses are two `Prescription` nodes.

10. **Reification is what makes `status: ACTIVE` possible** — and therefore what
    lets `ddi_rule` ignore a drug the patient stopped taking in March.

### The three tests, together

```
  said ABOUT it / found FROM it?      →  make it a node
  does direction carry meaning?       →  store it; else query undirected
  more than one, changing over time?  →  reify it
```
