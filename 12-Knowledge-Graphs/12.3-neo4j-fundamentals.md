## The core idea in one line

**`CREATE` always makes something new; `MERGE` finds-or-creates but matches on
every property you put inside it — so put only identity there, and let a
database constraint enforce what a coding convention cannot.**

## 1. Cypher is drawn, not written

Cypher is Neo4j's query language. Its central idea: **you draw the pattern you
mean.**

Creating a node:

```cypher
CREATE (w:Drug {name: "Warfarin", drugbank_id: "DB00682"})
```

Creating a relationship:

```cypher
CREATE (w:Drug {name: "Warfarin"})-[:INTERACTS_WITH {severity: "HIGH"}]->(a:Drug {name: "Aspirin"})
```

Compare that to the ASCII diagrams from 12.1 and 12.2:

```
   (Warfarin:Drug) ──INTERACTS_WITH {severity: HIGH}──► (Aspirin:Drug)
```

Same picture, different punctuation.

### The five pieces of syntax

```cypher
CREATE (w:Drug {name: "Warfarin"})-[:INTERACTS_WITH {severity: "HIGH"}]->(a:Drug {name: "Aspirin"})
        │ │      │                    │              │
        │ │      │                    │              └── property on the relationship
        │ │      │                    └── relationship TYPE (the colon marks it)
        │ │      └── property on the node
        │ └── node LABEL — what kind of thing this is (the colon marks it)
        └── variable — a temporary name so you can refer to this node later
```

| Symbol | Means |
|---|---|
| `( )` | a **node** |
| `[ ]` | a **relationship** |
| `-->` | direction |
| `{ }` | properties |
| `:` | a label or a relationship type |

**Why the colon?** It marks a *type name*, part of the graph's **structure**.
`:Drug` is a label, `:INTERACTS_WITH` is a relationship type. Properties like
`name` and `severity` are **data** stored inside, so they use plain
`key: value`.

**What is `w`?** A **variable**, existing only for the duration of this one
query. It lets you mention the same node twice:

```cypher
MATCH (w:Drug {name: "Warfarin"})
RETURN w.name, w.drugbank_id        -- 'w' refers back to the matched node
```

If you never need to refer back, omit it entirely — which is why the
relationship above is `[:INTERACTS_WITH ...]` with nothing before the colon.

## 2. `CREATE` is unconditional

```cypher
CREATE (d:Drug {name: "Warfarin"})     -- ALWAYS makes a new node
MERGE  (d:Drug {name: "Warfarin"})     -- makes one only if none matches
```

`ingest_ddi.py` reads a DrugBank export and loads interactions. Warfarin appears
in hundreds of rows.

```
  row 1:   Warfarin + Aspirin      →  CREATE (Warfarin) ... node #1
  row 2:   Warfarin + Ibuprofen    →  CREATE (Warfarin) ... node #2
  row 3:   Warfarin + Phenytoin    →  CREATE (Warfarin) ... node #3
  ...
```

**The duplication does not wait for a second run.** It is already there after
the first.

**Verified** (5 interaction rows, one run):

```
  rows processed        : 5
  Warfarin nodes        : 5   <- after ONE run
  total nodes           : 10
```

Run the script again next month for the v5.2 release, which adds one new
interaction:

```
  Warfarin nodes now    : 11
```

More than doubled — 5 from run 1, 6 from run 2.

```
   WHAT YOU WANTED                    WHAT YOU GOT
   ──────────────                     ────────────
                                       (Warfarin#1) ──► Aspirin
        (Warfarin)                     (Warfarin#2) ──► Ibuprofen
       ╱    │    ╲                     (Warfarin#3) ──► Phenytoin
  Aspirin Ibupro Phenytoin             ...
                                       5 separate nodes, each with exactly
   one node, three edges               one edge. No node knows the others exist.
```

## 3. ⚠️ Correction — what duplicates actually break

**A claim made during the lesson, and why it was wrong.**

> ❌ *"The query `MATCH (d:Drug {name:'Warfarin'})-[:INTERACTS_WITH]-(other)`
> matches Warfarin#1 and returns one interaction out of five."*

**Verified — this is false:**

```
  CLAIM I MADE: 'the query returns 1 of 5 interactions'
  ACTUAL      : ['Amiodarone', 'Aspirin', 'Fluconazole', 'Ibuprofen', 'Phenytoin']  -> 5 of 5
```

**Cypher `MATCH` binds *every* node fitting the pattern, not one.** A query
anchored directly on `{name: "Warfarin"}` finds all five duplicates and follows
all five edges. The interactions are not lost by that particular query.

So what *does* go wrong? Three things, all verified, and the second is serious.

### Damage 1 — result and count inflation

```
  MATCH (d:Drug {name:'Warfarin'}) RETURN d  -> 5 rows for ONE drug
  any COUNT/aggregate over drugs is now wrong by 5x
```

Every aggregate over the graph is inflated by an unknown, uneven factor. "How
many drugs interact with Warfarin?" returns 5× the truth.

### Damage 2 — traversal reaches ONE duplicate ✅ *this is the real fragmentation*

When you arrive at Warfarin by *traversing from somewhere else*, you land on
whichever duplicate that edge happens to point at:

```
  P001 ──TAKES──► (Warfarin#1) ──INTERACTS_WITH──► Aspirin
                       │
                       └── the other 4 edges hang off Warfarin#2..#5,
                           which P001 has no path to.
```

**Verified:**

```
  P001 -TAKES-> node index [0]  (one specific Warfarin node)
  now traverse P001 -> Warfarin -> INTERACTS_WITH -> ['Aspirin']
  1 of 5 interactions.  <-- THIS is the fragmentation.
```

**One of five.** And notice this is exactly the clinical query — start at the
patient, walk to their drugs, walk to the interactions. The 12.1 traversal.
`ddi_rule` would report one interaction where five exist, with no error and no
sign anything was missed.

The corrected statement:

> **Duplicates do not break lookups anchored on the duplicated node. They break
> every traversal that *arrives* at it — because an incoming edge points at one
> duplicate, and the rest are unreachable from there.**

### Damage 3 — writes hit one duplicate

```
  SET d.recalled = true  ->  1 of 5 Warfarin nodes updated
  the graph now disagrees with itself about whether Warfarin is recalled.
```

This is 12.1's **drift**, now inside a single graph.

## 4. `MERGE` — find-or-create

```cypher
MERGE (d:Drug {name: "Warfarin"})
```

Read as *"find this node, or create it if absent."*

**Verified — the same script, twice:**

```
  after run 1: Warfarin nodes = 1, total nodes = 6
  after run 2: Warfarin nodes = 1, total nodes = 6
  query returns : ['Amiodarone', 'Aspirin', 'Fluconazole', 'Ibuprofen', 'Phenytoin']  (5 distinct)
```

Run 2 changes nothing. That property has a name: the script is **idempotent** —
running it twice leaves the database in the same state as running it once. Full
treatment in 12.7.

## 5. The `MERGE` trap

```cypher
MERGE (d:Drug {name: "Warfarin", last_updated: "2026-08-30"})
```

**`MERGE` matches on the ENTIRE pattern, every property included.** It does not
ask "is there a Drug called Warfarin?" It asks "is there a Drug with name
Warfarin **and** `last_updated` 2026-08-30?"

```
  day 1:  MERGE (:Drug {name:"Warfarin", last_updated:"2026-08-29"})
          → nothing matches → CREATE     → node #1

  day 2:  MERGE (:Drug {name:"Warfarin", last_updated:"2026-08-30"})
          → node #1 has 08-29, not 08-30
          → the pattern does not match
          → CREATE                        → node #2
```

**Verified:**

```
  after MERGE with last_updated=2026-08-29: 1 Warfarin node(s)
  after MERGE with last_updated=2026-08-30: 2 Warfarin node(s)
  after MERGE with last_updated=2026-08-31: 3 Warfarin node(s)
  -> one new node per run, forever. Same disaster as CREATE, slower.
```

### ✅ The fix — separate identity from data

```cypher
MERGE (d:Drug {drugbank_id: "DB00682"})     -- match on IDENTITY only
SET   d.name         = "Warfarin",          -- then set mutable data
      d.last_updated = "2026-08-30"
```

**Verified:**

```
  after run: 1 node(s), last_updated=2026-08-29
  after run: 1 node(s), last_updated=2026-08-30
  after run: 1 node(s), last_updated=2026-08-31
```

One node, newest values, however many times it runs.

> **Put only identifying properties inside `MERGE`. Everything mutable goes in
> `SET`.**

Two refinements:

```cypher
MERGE (d:Drug {drugbank_id: "DB00682"})
ON CREATE SET d.first_seen = datetime()     -- only when the node is new
ON MATCH  SET d.last_seen  = datetime()     -- only when it already existed
```

### What *is* a drug's identity?

`name` is a poor choice — "Warfarin", "warfarin", "Warfarin sodium" and
"Coumadin" are four strings for one drug, and 12.2 showed where that leads. A
stable external identifier is better:

```cypher
MERGE (d:Drug {drugbank_id: "DB00682"})
SET   d.name = "Warfarin"
```

`DB00682` never changes and has exactly one spelling.

## 6. Constraint vs convention

A **convention** is a rule that lives in your code and your head:

```python
def add_drug(tx, drugbank_id, name):
    tx.run("MERGE (d:Drug {drugbank_id: $id}) SET d.name = $name",
           id=drugbank_id, name=name)
```

Correct code. But the rule "drugs are identified by drugbank_id" exists only
inside this function. **The database has never heard of it.**

A **constraint** is a rule that lives in the database:

```cypher
CREATE CONSTRAINT drug_id_unique IF NOT EXISTS
FOR (d:Drug) REQUIRE d.drugbank_id IS UNIQUE;
```

The difference is **who has to cooperate**:

```
                          ┌──────────────────┐
   your add_drug()   ────►│                  │
   a partner's ETL   ────►│      Neo4j       │
   Neo4j Browser     ────►│                  │
   a colleague's fix ────►│                  │
   a 2am hotfix      ────►└──────────────────┘
                                  ▲
   CONVENTION:  correct only if ALL FIVE go through add_drug()
   CONSTRAINT:  correct regardless of which one writes
```

**Verified — convention:**

```
  db.merge("Drug", drugbank_id="DB00682")                    # ingest_ddi.py  ✓
  db.create("Drug", drugbank_id="DB00682", name="Coumadin")  # raw console    ✗
    duplicate created: 2 nodes. No error raised.
```

**Verified — constraint:**

```
    ConstraintValidationFailed: Node already exists with label `Drug`
    and property `drugbank_id` = 'DB00682'
    nodes: 1
```

The failure modes differ in the way that matters:

```
  convention broken  →  a duplicate node is created
                        no error, graph silently fragments,
                        traversals return a fraction of the truth

  constraint broken  →  ConstraintValidationFailed
                        rejected loudly, at the moment it happens
```

This is Chapter 11's principle again — the one behind Pydantic. `patient.py`
does not *ask* every function to check the weight; it makes an invalid weight
impossible to construct.

### ⚠️ Add constraints on day one

**Verified:**

```
  a constraint cannot be added to an already-dirty database:
    cannot create constraint: duplicate Drug.drugbank_id already present
    -> you must de-duplicate FIRST.
```

A uniqueness constraint cannot be created if duplicates already exist. Once a
`CREATE`-based script has fragmented the graph, you must clean up before the
database will let you prevent it happening again. This is why
`constraints.cypher` runs **before** any ingestion.

### What Neo4j can and cannot enforce

| Can enforce | Example |
|---|---|
| uniqueness | `REQUIRE d.drugbank_id IS UNIQUE` |
| existence | `REQUIRE d.name IS NOT NULL` |
| composite key | `REQUIRE (v.chrom, v.pos) IS NODE KEY` |
| property type | `REQUIRE d.name IS :: STRING` |

**Cannot enforce:** anything comparing two nodes to each other — "edges must
point alphabetically" (12.2), "a patient's active prescriptions must not exceed
20", "this edge's severity must match its source's severity." Those stay in
application code, and you design so their failure is *loud* rather than silent.

> **Whenever you catch yourself saying "we always do X" about the database, ask
> whether the database can enforce X. If it can, make it. If it can't, that is a
> signal to redesign — not to rely on discipline.**

### Free performance

A uniqueness constraint creates an index underneath. So
`MATCH (d:Drug {drugbank_id: "DB00682"})` becomes a direct lookup instead of a
scan across every Drug node.

## 7. The real `constraints.cypher`

```cypher
-- Run this BEFORE any ingestion script. Order matters.

CREATE CONSTRAINT drug_id_unique IF NOT EXISTS
FOR (d:Drug) REQUIRE d.drugbank_id IS UNIQUE;

CREATE CONSTRAINT gene_symbol_unique IF NOT EXISTS
FOR (g:Gene) REQUIRE g.symbol IS UNIQUE;

CREATE CONSTRAINT disease_id_unique IF NOT EXISTS
FOR (d:Disease) REQUIRE d.mondo_id IS UNIQUE;

CREATE CONSTRAINT variant_key IF NOT EXISTS
FOR (v:Variant) REQUIRE (v.chromosome, v.position, v.alt) IS NODE KEY;

CREATE CONSTRAINT drug_name_exists IF NOT EXISTS
FOR (d:Drug) REQUIRE d.name IS NOT NULL;
```

`IF NOT EXISTS` makes the file itself idempotent — safe to re-run on every
deploy, which is the same property `MERGE` gives your data.

The `Variant` constraint is a **composite key**: no single property identifies a
genetic variant, but chromosome + position + alternate allele together do.

## 8. Runnable file

```python
"""12.3 — CREATE vs MERGE vs constraints, using a faithful
   simulation of Neo4j's semantics. No database required."""


class ConstraintValidationFailed(Exception):
    pass


class FakeNeo4j:
    def __init__(self):
        self.nodes = []          # [{"_label": ..., **props}]
        self.edges = []          # [(start_idx, type, end_idx, props)]
        self.constraints = []    # [(label, prop)]

    def add_unique_constraint(self, label, prop):
        seen = [n.get(prop) for n in self.nodes if n["_label"] == label]
        if len(seen) != len(set(seen)):
            raise ConstraintValidationFailed(
                f"duplicate {label}.{prop} already present — de-duplicate first")
        self.constraints.append((label, prop))

    def _check(self, label, props):
        for clabel, cprop in self.constraints:
            if clabel == label and cprop in props and any(
                    n["_label"] == label and n.get(cprop) == props[cprop]
                    for n in self.nodes):
                raise ConstraintValidationFailed(
                    f"Node already exists with `{label}`.`{cprop}` "
                    f"= {props[cprop]!r}")

    def create(self, label, **props):
        """Unconditional — this is what shreds a graph."""
        self._check(label, props)
        self.nodes.append({"_label": label, **props})
        return len(self.nodes) - 1

    def merge(self, label, **props):
        """Matches the ENTIRE pattern; creates only if nothing matches."""
        for i, n in enumerate(self.nodes):
            if n["_label"] == label and all(n.get(k) == v
                                            for k, v in props.items()):
                return i
        return self.create(label, **props)

    def set_props(self, idx, **props):
        self.nodes[idx].update(props)

    def count(self, label, **props):
        return sum(1 for n in self.nodes if n["_label"] == label
                   and all(n.get(k) == v for k, v in props.items()))

    def relate(self, a, reltype, b, **props):
        self.edges.append((a, reltype, b, props))


PARTNERS = ["Aspirin", "Ibuprofen", "Phenytoin", "Amiodarone", "Fluconazole"]

# ── CREATE fragments the graph ───────────────────────────────────
db = FakeNeo4j()
warfarins = []
for p in PARTNERS:
    w = db.create("Drug", name="Warfarin")
    db.relate(w, "INTERACTS_WITH", db.create("Drug", name=p))
    warfarins.append(w)
print(f"CREATE, one run -> {db.count('Drug', name='Warfarin')} Warfarin nodes")

# the damage: a traversal ARRIVING at Warfarin reaches only one duplicate
p001 = db.create("Patient", name="P001")
db.relate(p001, "TAKES", warfarins[0])
reached = [e for s, t, e, _ in db.edges if s == p001 and t == "TAKES"]
found = [db.nodes[e]["name"] for r in reached
         for s, t, e, _ in db.edges if t == "INTERACTS_WITH" and s == r]
print(f"  P001 -> Warfarin -> interactions: {found}"
      f"   ({len(found)} of {len(PARTNERS)})")

# ── MERGE is idempotent ──────────────────────────────────────────
db = FakeNeo4j()
for _ in range(2):
    for p in PARTNERS:
        db.relate(db.merge("Drug", name="Warfarin"),
                  "INTERACTS_WITH", db.merge("Drug", name=p))
print(f"MERGE, two runs -> {db.count('Drug', name='Warfarin')} Warfarin node")

# ── the MERGE trap, and the fix ──────────────────────────────────
db = FakeNeo4j()
for day in ["2026-08-29", "2026-08-30", "2026-08-31"]:
    db.merge("Drug", name="Warfarin", last_updated=day)
print(f"MERGE with mutable prop -> "
      f"{db.count('Drug', name='Warfarin')} nodes  (one per run)")

db = FakeNeo4j()
for day in ["2026-08-29", "2026-08-30", "2026-08-31"]:
    i = db.merge("Drug", drugbank_id="DB00682")
    db.set_props(i, name="Warfarin", last_updated=day)
print(f"MERGE on identity + SET -> "
      f"{db.count('Drug', drugbank_id='DB00682')} node")

# ── constraint vs convention ─────────────────────────────────────
db = FakeNeo4j()
db.merge("Drug", drugbank_id="DB00682")
db.create("Drug", drugbank_id="DB00682", name="Coumadin")     # bypasses helper
print(f"convention -> {db.count('Drug', drugbank_id='DB00682')} nodes, no error")

db = FakeNeo4j()
db.add_unique_constraint("Drug", "drugbank_id")
db.merge("Drug", drugbank_id="DB00682")
try:
    db.create("Drug", drugbank_id="DB00682", name="Coumadin")
except ConstraintValidationFailed as e:
    print(f"constraint -> rejected: {e}")
```

## 9. Never forget

1. **Cypher is drawn:** `()` node, `[]` relationship, `-->` direction, `{}`
   properties, `:` label or type. A colon means "type name," not data.

2. **A variable like `w` exists only inside one query.** Omit it when you never
   refer back.

3. **`CREATE` is unconditional.** It duplicates on the *first* run, not the
   second — once per row mentioning the entity.

4. **Duplicates do NOT break lookups anchored on the duplicated node** —
   `MATCH` binds every match. ❌ The claim that "the query returns 1 of 5" is
   wrong for that form of query.

5. **Duplicates DO break every traversal that *arrives* at the node.** An
   incoming edge points at one duplicate; the rest are unreachable from there.
   `P001 → Warfarin → interactions` returned **1 of 5**. That is the real
   fragmentation, and it is exactly the clinical query.

6. **Duplicates also inflate every aggregate and split every write.** `SET`
   touched 1 of 5 nodes — drift, inside one graph.

7. **`MERGE` matches the ENTIRE pattern.** One mutable property inside it means
   one new node per run — the same disaster as `CREATE`, arriving slowly.

8. **`MERGE` on identity, `SET` for everything else.** Prefer a stable external
   ID (`drugbank_id`) over a name, which has spellings.

9. **A convention is enforced by discipline; a constraint by the database.** The
   convention holds until one write bypasses your helper — and that write raises
   no error.

10. **Constraints must exist before the first ingestion.** A uniqueness
    constraint cannot be added to a database that already contains duplicates.

11. **If you catch yourself saying "we always do X," ask whether the database
    can enforce X.** If it can't, redesign rather than rely on memory.
