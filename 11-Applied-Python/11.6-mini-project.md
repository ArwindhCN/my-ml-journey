## The brief

A placement portal at Amrita. Companies post eligibility criteria; students
apply; the engine decides whether each student may sit for a drive **and
explains why**.

The stakes shape the design. Wrongly *blocking* an eligible student costs them a
job they would have got, and there is no appeal once the drive closes. Wrongly
*passing* an ineligible one wastes a slot and embarrasses the placement cell.
Both errors are real, so the system must be auditable in both directions — every
verdict has to name the rule and the document it came from.

```
   Academic DB          Placement Engine           Student's screen
   ───────────          ────────────────           ────────────────
   student JSON  ────►   validate (11.1)    ────►  ELIGIBLE / BLOCKED
   company JSON  ────►   apply rules (11.2)        + every reason
                         resolve names (11.3)      + what did NOT run
                         shape output (11.4)
                         run concurrently (11.5)
```

## Part 1 — The boundary (11.1)

Everything downstream trusts this layer, so it does all the doubting.

```python
class Student(BaseModel):
    model_config = ConfigDict(extra="forbid")

    student_id:         str
    cgpa:               float = Field(..., ge=0.0,  le=10.0)
    active_backlogs:    int   = Field(..., ge=0,    le=50)
    history_of_arrears: int   = Field(..., ge=0,    le=100)
    attendance_pct:     float = Field(..., ge=0.0,  le=100.0)
    branch:             str
    graduation_year:    int   = Field(..., ge=2000, le=2100)
    offers_held:        int   = Field(..., ge=0,    le=20)
    highest_offer_lpa:  float = Field(default=0.0, ge=0.0, le=1000.0)
```

### Why each bound is what it is

| Field | Bound | Reasoning |
|---|---|---|
| `cgpa` | `ge=0, le=10` | Zero is achievable (a student who failed everything). Ten is the top of the scale — `11.5` is a data error, not a genius. |
| `attendance_pct` | `ge=0, le=100` | Zero attendance is a real, recordable state. Above 100 is impossible. |
| `active_backlogs` | `ge=0` | **Zero is the normal case, not an impossible one.** This is the newborn-vs-weight distinction from 11.1: `gt=0` here would reject every student in good standing. |
| `history_of_arrears` | `ge=0, le=100` | Same logic. The upper bound is a sanity ceiling, not a rule. |
| `graduation_year` | `ge=2000, le=2100` | Catches a `20226` typo that would otherwise sail through as a valid int. |

> **The `ge` vs `gt` decision is never syntactic.** For each field, ask whether
> zero is a real value someone could legitimately have. CGPA: yes. Attendance:
> yes. Backlogs: yes, and it's the *best* case. Weight in a hospital: no.

### Three checks a `Field` constraint cannot express

**1. Format — the roll number**

```python
@field_validator("student_id")
@classmethod
def valid_roll_format(cls, v: str) -> str:
    if not re.fullmatch(r"CB\.EN\.U4[A-Z]{3}\d{5}", v.strip().upper()):
        raise ValueError("student_id must look like CB.EN.U4CSE22045")
    return v.strip().upper()
```

Note it **returns a cleaned value**. A validator can normalise as well as
reject — `" cb.en.u4cse22045 "` becomes canonical before any rule sees it.

**2. Cross-field — arrears consistency**

```python
@model_validator(mode="after")
def arrears_consistency(self) -> "Student":
    if self.active_backlogs > self.history_of_arrears:
        raise ValueError("active_backlogs cannot exceed history_of_arrears")
    return self
```

Neither field is invalid alone. `active=3` is fine. `history=1` is fine. The
contradiction lives **between** them — an active backlog is by definition part of
your history, so active can never exceed total. This is the same shape as
11.1's duplicate-drug rule: it needs a wider scope than one field has.

`mode="after"` matters — it runs *after* type coercion, so both values are
guaranteed to be real `int`s by the time you compare them.

**3. Cross-field — offer consistency**

```python
@model_validator(mode="after")
def offer_consistency(self) -> "Student":
    if self.offers_held == 0 and self.highest_offer_lpa > 0:
        raise ValueError("highest_offer_lpa must be 0 when offers_held is 0")
    if self.offers_held > 0 and self.highest_offer_lpa == 0:
        raise ValueError("highest_offer_lpa must be > 0 when offers_held is > 0")
    return self
```

This one is load-bearing. The placement-policy rule divides by
`highest_offer_lpa`; an inconsistent pair would silently produce a nonsense
verdict. **Catching it at the door is what allows the rule to skip the check.**

### `extra="forbid"` — the typo catcher

```python
model_config = ConfigDict(extra="forbid")
```

Without it, `{"CGPA": 8.0}` (wrong case) is *silently dropped*, and you get
"cgpa: Field required" with no hint that a near-miss field was sent. With it,
you get both errors and the cause is obvious.

### Verified — what the door rejects

```
  CGPA above scale       -> rejected [cgpa]            Input should be less than or equal to 10
  negative attendance    -> rejected [attendance_pct]  Input should be greater than or equal to 0
  bad roll format        -> rejected [student_id]      must look like CB.EN.U4CSE22045
  active > history       -> rejected [(model)]         active_backlogs cannot exceed history_of_arrears
  placed but 0 LPA       -> rejected [(model)]         highest_offer_lpa must be > 0 when offers_held is > 0
  typo'd field name      -> rejected [cgpa]            Field required

  coercion (lax mode): cgpa='7.84' -> 7.84  |  branch ' cse ' -> CSE
```

The last line is Pydantic's **lax mode** doing useful work: a string CGPA from a
CSV export is coerced to a float rather than rejected, and the branch validator
normalises whitespace and case. Cleaning at the door means no rule downstream
needs a `.strip().upper()`.

### The company side

```python
class Criteria(BaseModel):
    model_config = ConfigDict(extra="forbid")

    company:             str
    min_cgpa:            float = Field(..., ge=0.0, le=10.0)
    max_active_backlogs: int   = Field(..., ge=0,   le=50)
    max_history_arrears: int   = Field(..., ge=0,   le=100)
    min_attendance_pct:  float = Field(..., ge=0.0, le=100.0)
    allowed_branches:    List[str]
    package_lpa:         float = Field(..., gt=0.0, le=1000.0)

    @field_validator("allowed_branches")
    @classmethod
    def no_duplicate_branches(cls, v):
        names = [b.strip().upper() for b in v]
        if len(names) != len(set(names)):
            raise ValueError("duplicate branch in allowed_branches")
        if not names:
            raise ValueError("allowed_branches cannot be empty")
        return names
```

Note `package_lpa` uses **`gt=0`**, unlike every field on `Student`. A company
offering zero LPA isn't a low offer, it's a broken record. Different field,
different question, different operator.

An **empty** `allowed_branches` is also rejected. An empty list would silently
block every student on earth — a data-entry slip producing a total outage with
no error.

## Part 2 — Pure rules (11.2)

Every rule has the identical signature and the identical discipline:

```
  (student, criteria, service)  ->  Finding | None
```

No rule modifies the student. No rule reads another rule's result. No rule
knows its position in the list.

```python
def rule_cgpa(s: Student, c: Criteria, _svc=None) -> Optional[Finding]:
    if s.cgpa < c.min_cgpa:
        return Finding(
            rule_id="CGPA_BELOW_CUTOFF", severity="HARD_BLOCK",
            explanation=f"CGPA {s.cgpa} is below the required {c.min_cgpa}.",
            evidence=f"{c.company} eligibility notice, CGPA clause",
            source=f"{c.company} JD 2026")
    return None
```

### Contestability is designed in

Every `Finding` carries `evidence` and `source`. A student appealing to the
placement cell can say *"blocked under the Freshworks arrears clause"* rather
than *"the portal said no."* That is the contestability idea from 11.2 — not
just being able to understand the output, but being able to **argue against it
on the record**, citing what it cited.

A machine-learning classifier trained on past placement outcomes would give
`0.31` and nothing to appeal against. Worse, it would have learned every bias in
the historical data — which branches got hired, which hostels, which schools.
**A rule has no training set, so it has no inherited bias.**

### Severity is a three-way distinction, not a boolean

```
  HARD_BLOCK   the student cannot sit. Full stop.
  SOFT_BLOCK   blocked, but a documented waiver exists (attendance condonation)
  INFO         not a block — context the student should see
```

`SOFT_BLOCK` exists because attendance shortfall is condonable under Amrita's
regulations. Collapsing it into `HARD_BLOCK` would hide a legitimate route;
collapsing it into `INFO` would imply the student can just walk in. The middle
category is the honest one.

### The most interesting rule

```python
def rule_placement_policy(s, c, _svc=None):
    """One-offer policy: a placed student may only apply for a materially
       better package (>= 1.5x their current highest)."""
    if s.offers_held == 0:
        return None
    if c.package_lpa >= s.highest_offer_lpa * 1.5:
        return Finding(rule_id="DREAM_OFFER_PERMITTED", severity="INFO", ...)
    return Finding(rule_id="ALREADY_PLACED", severity="HARD_BLOCK", ...)
```

Three branches, and the middle one returns `INFO` — a finding that is *not* a
block. This is why `evaluate()` decides the verdict from severities rather than
from "did any rule return something." **A rule that fires is not automatically
a rejection.**

### Verified — one student, four companies

Arwindh: CGPA 7.84, 0 active backlogs, 2 historical arrears, 71.5% attendance,
CSE, already placed at 8.5 LPA.

```
  Zoho (9.0 LPA) -> BLOCKED
     [SOFT_BLOCK] ATTENDANCE_SHORT       71.5% is below 75.0%. Condonation may apply.
     [HARD_BLOCK] ALREADY_PLACED         9.0 LPA is below the 1.5x dream-offer bar.

  Freshworks (12.0 LPA) -> BLOCKED
     [HARD_BLOCK] CGPA_BELOW_CUTOFF      7.84 is below the required 8.0.
     [HARD_BLOCK] ARREARS_HISTORY        2 historical arrears; maximum permitted is 0.
     [SOFT_BLOCK] ATTENDANCE_SHORT       71.5% is below 75.0%.
     [HARD_BLOCK] ALREADY_PLACED         12.0 LPA is below the 1.5x bar.

  TCS (7.0 LPA) -> BLOCKED
     [HARD_BLOCK] ALREADY_PLACED         7.0 LPA is below the 1.5x bar.

  Google (45.0 LPA) -> BLOCKED
     [HARD_BLOCK] CGPA_BELOW_CUTOFF      7.84 is below the required 8.5.
     [HARD_BLOCK] ARREARS_HISTORY        2 historical arrears; maximum permitted is 0.
     [SOFT_BLOCK] ATTENDANCE_SHORT       71.5% is below 75.0%.
     [INFO      ] DREAM_OFFER_PERMITTED  45.0 LPA qualifies as a dream offer.
```

**Read the Google result carefully.** The dream-offer rule *permits* the
application — 45 LPA clears the 1.5× bar comfortably. The student is still
blocked, on CGPA and arrears. Both facts are reported. A system that returned
only the first blocking reason would tell this student "CGPA too low" and they'd
never learn the arrears also disqualified them, or that the one-offer policy
wasn't the obstacle they assumed.

> **This is the 11.5 early-`return` lesson applied at design time.** Collect every
> finding; never stop at the first.

### Verified — order independence

```
  6 shuffled rule orders -> 1 distinct result: {('ALREADY_PLACED', 'ATTENDANCE_SHORT')}
```

Because no rule mutates anything, the rule list can be reordered, parallelised,
or unit-tested one function at a time. If any rule edited the student, that
number would be greater than 1 and the placement cell would have a system whose
answer depended on list ordering nobody documented.

## Part 3 — Honest failure (11.2)

Six rules read only the two objects. One needs the registrar:

```python
def rule_disciplinary(s, c, svc):
    if svc.has_active_hold(s.student_id):
        return Finding(rule_id="DISCIPLINARY_HOLD", severity="HARD_BLOCK", ...)
    return None
```

The registrar service can be down. The catastrophic implementation is
`except: return None` — because `None` means *"I checked, no hold exists."* An
unreachable service would be silently converted into a clean bill of conduct.

```python
def evaluate(student, criteria, svc) -> EligibilityResponse:
    findings, completed, failed = [], [], []

    for rule in RULES:
        try:
            result = rule(student, criteria, svc)
            completed.append(rule.__name__)
            if result:
                findings.append(result)
        except ServiceUnavailable:
            failed.append(rule.__name__)
            findings.append(Finding(
                rule_id="CHECK_UNAVAILABLE", severity="SYSTEM",
                explanation=f"{rule.__name__} could not complete. This "
                            f"student was NOT screened on that criterion.",
                evidence="", source="unavailable"))

    if any(f.severity == "SYSTEM" for f in findings):
        verdict = "CHECK_UNAVAILABLE"
    elif any(f.severity in ("HARD_BLOCK", "SOFT_BLOCK") for f in findings):
        verdict = "BLOCKED"
    else:
        verdict = "ELIGIBLE"
    ...
```

Three deliberate choices:

**The `try` wraps each rule, not the loop.** Six rules that never touch the
registrar keep working. Losing CGPA screening because a disciplinary service is
down would be absurd.

**`CHECK_UNAVAILABLE` is its own verdict**, not a variant of ELIGIBLE or
BLOCKED. "We don't know" is a third state and must be representable as one.

**A SYSTEM finding overrides everything.** Even if no rule blocked, the verdict
is not ELIGIBLE — because one criterion was never evaluated. Silence about an
unchecked criterion is exactly the failure mode this chapter exists to prevent.

### Verified — registrar down

```
  verdict          : CHECK_UNAVAILABLE
  checks_completed : 6
  checks_failed    : ['rule_disciplinary']
  system finding   : ['rule_disciplinary could not complete. This student was NOT screened...']
```

## Part 4 — The hybrid path (11.3)

Branch names arrive from a dozen sources in a dozen spellings. The architecture
is **rules → statistics → rules**:

```
  raw string
      │
      ▼
  ┌────────────────────────────────────────────┐
  │  1. RULES: normalise, exact + alias lookup │  exact, free, no failure mode
  └────────────────────────────────────────────┘
      │ no match
      ▼
  ┌────────────────────────────────────────────┐
  │  2. STATISTICS: fuzzy character matching   │  the residual only
  └────────────────────────────────────────────┘
      │ candidate + confidence
      ▼
  ┌────────────────────────────────────────────┐
  │  3. RULES: confidence gate                 │
  │     ≥ 0.90 → accept                        │
  │     < 0.90 → HUMAN_REVIEW                  │  never auto-accept a guess
  └────────────────────────────────────────────┘
```

```python
def resolve_branch(raw: str, threshold: float = 0.90) -> BranchMatch:
    s = re.sub(r"[^A-Z& ]", " ", raw.upper())
    s = re.sub(r"\s+", " ", s).strip()

    if s in CANONICAL_BRANCHES:                       # STAGE 1
        return BranchMatch(..., method="exact", confidence=1.0, action="ACCEPT")
    if s in ALIASES:
        return BranchMatch(..., method="alias", confidence=1.0, action="ACCEPT")

    pool = CANONICAL_BRANCHES + list(ALIASES)         # STAGE 2
    close = difflib.get_close_matches(s, pool, n=1, cutoff=0.6)
    if not close:
        return BranchMatch(..., confidence=0.0, action="HUMAN_REVIEW")

    cand = close[0]
    conf = difflib.SequenceMatcher(None, s, cand).ratio()

    if conf >= threshold:                             # STAGE 3
        return BranchMatch(..., action="ACCEPT")
    return BranchMatch(..., resolved=None, action="HUMAN_REVIEW")
```

**Verified:**

```
  CSE                                exact  conf=1.0    ACCEPT        -> CSE
  Computer Science                   alias  conf=1.0    ACCEPT        -> CSE
  cse                                exact  conf=1.0    ACCEPT        -> CSE
  COMPUTER SCIENCE AND ENGINEERING   alias  conf=1.0    ACCEPT        -> CSE
  E&C                                alias  conf=1.0    ACCEPT        -> ECE
  Mechnical                          fuzzy  conf=0.947  ACCEPT        -> MECH
  Compter Sciene                     fuzzy  conf=0.933  ACCEPT        -> CSE
  Nanotechnology                     fuzzy  conf=0.722  HUMAN_REVIEW  -> None
```

Five of eight resolved by **rules alone** — exact, free, zero chance of error.
Running a model on `"CSE"` would spend a probabilistic method on a solved
problem and introduce a failure mode where none existed.

Two typos resolved by fuzzy matching above threshold. `"Nanotechnology"` — a
real branch that simply isn't in the list — came back at 0.722 and was **routed
to a human rather than guessed at**. The system does not hallucinate a nearest
match.

Note this uses **`difflib`, not embeddings**. Character-level similarity is the
right tool for typos and abbreviations. Embeddings compare *meaning* and would
be the tool if you needed `"the CS branch"` → `CSE`. Reach for the cheapest
method that solves the problem.

### The threshold is a policy decision, not a tuning parameter

At 0.90, `"Mechnical"` (0.947) is auto-accepted. Raise it to 0.95 and that goes
to human review instead. The right value depends on the cost asymmetry: a wrong
branch could block an eligible student from a drive they qualified for. Given
that, erring toward review is defensible. **Whoever sets this number is making a
policy choice and should be named in a comment.**

## Part 5 — The outbound contract (11.4)

```python
Verdict  = Literal["ELIGIBLE", "BLOCKED", "CHECK_UNAVAILABLE"]
Severity = Literal["INFO", "SOFT_BLOCK", "HARD_BLOCK", "SYSTEM"]

class Finding(BaseModel):
    model_config = ConfigDict(extra="forbid")
    rule_id:     str
    severity:    Severity
    explanation: str
    evidence:    str
    source:      str

class EligibilityResponse(BaseModel):
    model_config = ConfigDict(extra="forbid")
    student_id:       str
    company:          str
    verdict:          Verdict
    findings:         List[Finding] = []
    checks_completed: List[str] = []
    checks_failed:    List[str] = []
```

`Literal` on both `verdict` and `severity` because the frontend switches on
them — badge colour, icon, sort order. A developer writing `"Severe"` instead of
`"HARD_BLOCK"` would produce a colourless badge on the most serious finding on
the page, with no error anywhere in the stack.

**Verified — both classes of mistake blocked at the source:**

```
  severity='Severe'  -> rejected: literal_error
  renamed field      -> [('explanation', 'missing'), ('message', 'extra_forbidden')]
```

The rename produces **two** errors, which is what makes it debuggable.
`extra="forbid"` is what turns "explanation is required" (baffling) into
"explanation is required AND message isn't a field" (obvious).

`checks_completed` and `checks_failed` exist because **an empty `findings` list
is ambiguous.** It could mean "student cleared everything" or "nothing ran." The
frontend can now render *"7 of 7 checks completed"* rather than an unqualified
green tick.

**Verified wire format:**

```json
{
  "student_id": "CB.EN.U4CSE22045",
  "company": "Freshworks",
  "verdict": "BLOCKED",
  "findings": [
    {
      "rule_id": "ATTENDANCE_SHORT",
      "severity": "SOFT_BLOCK",
      "explanation": "Attendance 71.5% is below 75.0%. Condonation may apply.",
      "evidence": "Amrita academic regulations, attendance condonation clause",
      "source": "Amrita Academic Handbook 2025"
    },
    {
      "rule_id": "ARREARS_HISTORY",
      "severity": "HARD_BLOCK",
      "explanation": "2 historical arrears; maximum permitted is 0.",
      "evidence": "Freshworks eligibility notice, arrears clause",
      "source": "Freshworks JD 2026"
    }
  ],
  "checks_completed": ["rule_cgpa", "rule_active_backlogs", "..."],
  "checks_failed": []
}
```

## Part 6 — Concurrency (11.5)

Checking one student against every company on the portal is a batch of
independent evaluations, each containing a 40ms registrar call.

```python
async def evaluate_all_sequential(student, criteria_list, svc):
    return [evaluate(student, c, svc) for c in criteria_list]

async def evaluate_all_concurrent(student, criteria_list, svc):
    return await asyncio.gather(*[
        asyncio.to_thread(evaluate, student, c, svc) for c in criteria_list])
```

**Verified — 4 companies:**

```
  sequential :  161.1ms
  concurrent :   45.5ms   (3.5x faster)
```

`asyncio.to_thread` is used because `RegistrarService.has_active_hold` is a
**blocking** function — a plain synchronous call with no `await` inside. Passing
it directly to `gather` would not have helped; `gather` can only overlap things
that yield, and a blocking function never yields. Worse, calling it inside
`async def` on the event loop's single thread would freeze every other user on
the portal.

`to_thread` moves each blocking call onto its own thread and gives the event
loop an `await` to park on. That is the escape hatch for libraries with no async
version — slower than a native async driver, vastly better than blocking the
loop.

> **Why this is safe here:** the evaluations are independent. Nothing shared is
> mutated, because the rules are pure. Purity is what makes concurrency free —
> if any rule had edited the student, running four evaluations on four threads
> would be a race condition.

## Part 8 — What to extend, if you want to take it further

- **Add a `waiver` field** to `Student` and let a documented condonation turn a
  `SOFT_BLOCK` into an `INFO`. Note it belongs in the *rule*, not the model —
  the model records facts, the rule interprets them.
- **Version the criteria.** A company that changes its cutoff mid-season should
  not retroactively change last week's verdicts. Add `effective_from` and pass a
  date into `evaluate`.
- **Log every verdict** with the full `EligibilityResponse`. When a student
  appeals in three months, you need to reproduce the exact decision.
- **Write the pytest suite** — each rule is a pure function taking two objects,
  so each test is three lines. That is the payoff for purity, and it is Ch 18.4.

## Part 9 — Never forget

1. **The boundary does all the doubting so the rules can do none.** Every
   `.strip()`, every `if x is None`, every defensive check you would scatter
   through business logic belongs in the model instead.

2. **`ge` vs `gt` is a domain question, never a syntax one.** Ask whether zero
   is a real value someone could have. Backlogs: yes. Package offered: no.

3. **Cross-field contradictions need `@model_validator`.** Neither
   `active_backlogs=3` nor `history_of_arrears=1` is wrong alone. The invalidity
   lives between them.

4. **`extra="forbid"` turns a baffling error into an obvious one.** Without it a
   typo'd field is dropped in silence and you debug the wrong thing.

5. **Report every finding, never just the first.** The Google result blocked on
   two criteria and permitted on a third. A first-match-wins engine would have
   hidden two of those three facts.

6. **Severity is not a boolean.** `SOFT_BLOCK` exists because a documented
   waiver exists. Collapsing it in either direction lies to the student.

7. **Pure rules make everything else possible** — order independence, isolated
   tests, and safe concurrency all fall out of "no rule mutates anything."

8. **"Unknown" is a third verdict.** `CHECK_UNAVAILABLE` is not a flavour of
   ELIGIBLE. A SYSTEM finding overrides every other verdict, because an
   unevaluated criterion is not a passed one.

9. **Rules → statistics → gate.** Deterministic work first, statistics on the
   residual, a rule deciding whether the statistical answer is trustworthy
   enough to accept. Low confidence goes to a human, never to a guess.

10. **A confidence threshold is a policy decision.** Whoever picks 0.90 over
    0.95 is choosing which error to prefer, and should say so in writing.

11. **`Literal` for anything the frontend switches on.** A free-form `str` in a
    colour or routing key is an inverted safety signal waiting to happen.

12. **An empty result list is ambiguous.** "Nothing wrong" and "nothing ran"
    must be distinguishable in the payload itself.

13. **`gather` needs things that yield.** Blocking calls need `to_thread`, or
    they silently run sequentially — or worse, freeze the whole server.
