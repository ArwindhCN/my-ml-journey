## The core idea in one line

**A rule engine doesn't learn anything. Every number in it was put there by a
human who can be named — and that is the entire point.**

## 1. The trap: rules look exactly like decision trees

This is a trained Decision Tree (Ch 4):

```
                    egfr < 60 ?
                   ╱          ╲
                yes            no
                 │              │
            age > 65 ?      [no risk]
            ╱        ╲
         yes          no
          │            │
     [HIGH RISK]   [low risk]
```

This is a rule from `decision_engine.py`:

```python
def renal_risk_rule(patient):
    if patient.egfr < 60 and patient.age > 65:
        return Alert(
            risk_type="RENAL_RISK",
            severity="HIGH",
            evidence="KDIGO CKD staging guideline",
            source_database="KDIGO 2024",
        )
    return None
```

Side by side they are almost indistinguishable:

```
   Decision Tree (Ch 4)              Rule Engine (Ch 11.2)
   ────────────────────              ─────────────────────
   if egfr < 60:                     if egfr < 60 and age > 65:
       if age > 65:                      return HIGH_RISK
           return HIGH_RISK
```

Same structure, same features, same thresholds. **So what is actually
different?** Only one thing: *where the number 60 came from.*

---

## 2. Where the `60` came from — and two mistakes I made

### ❌ Mistake 1: "the decision tree learns it from gradient descent"

**Wrong.** Gradient descent needs a *differentiable* loss — a smooth surface you
can take a derivative of and roll downhill. A tree split is a **discrete
choice**: "split here or split there." There is nothing to differentiate.

Trees are built by **greedy impurity search**. At every node the algorithm tries
each candidate threshold on each feature, measures how well the resulting split
separates the classes (Gini impurity or entropy), keeps the winner, and recurses.

```
  Trying thresholds on egfr:

    < 30  →  Gini 0.44
    < 45  →  Gini 0.38
    < 60  →  Gini 0.21   ← best separation, keep it
    < 75  →  Gini 0.35
    < 90  →  Gini 0.47
```

**Keep these apart:** gradient descent belongs to Ch 9.5 (neural networks).
Trees (Ch 4) never touch it.

### ❌ Mistake 2: "the rule engine learns it from the knowledge graph"

**Wrong, and it's the same instinct misfiring.** *Nothing in a rule engine
learns.* Nothing is fitted to data at all.

The `60` came from a **nephrologist**. Specifically from the KDIGO staging
guideline, where eGFR below 60 mL/min/1.73m² defines Chronic Kidney Disease
stage 3. A human read the clinical literature and typed `60` into the file.

The Neo4j knowledge graph is likewise **stored curated facts**, not a trained
model — see §7.

### ✅ The actual difference

```
  DECISION TREE                       RULE ENGINE
  ─────────────                       ───────────
  60 came from:                       60 came from:
    your training data                  KDIGO clinical guideline
    ↓                                   ↓
    fitted by impurity search           typed in by a human
    ↓                                   ↓
    would be 58 or 63 on                stays 60 until a nephrologist
    a different dataset                 says otherwise
```

### What follows from that difference

| | Decision Tree | Rule Engine |
|---|---|---|
| **Justification** | "the data suggested it" | "KDIGO 2024, page 12" |
| **Changing it** | retrain on new data | edit one line |
| **If training data is biased** | threshold inherits the bias | unaffected — no data involved |
| **On a rare case** | unreliable, few samples seen | works identically, never saw *any* samples |

**The last row is the clinically decisive one.** This is the Ch 10.3 embedding
insight returning: *rare categories get few gradient updates and stay
near-random.* A learned model is weakest exactly where medicine needs it
strongest — the rare drug, the unusual patient.

> **A rule has no sample size. It never trained, so it cannot be undertrained.**

## 3. Contestability — the real reason for `evidence` and `source_database`

A Random Forest returns `0.87`. A rule returns:

```python
Alert(
    risk_type="RENAL_RISK",
    severity="HIGH",
    evidence="KDIGO CKD staging guideline",
    source_database="KDIGO 2024",
)
```

Scenario: a clinician has ~30 seconds per patient, is **legally accountable**
for the prescription, and **disagrees** with the alert.

With the `Alert`, they can override it and write in the notes:

> *Alert acknowledged — KDIGO renal threshold. Overridden: patient's eGFR is
> depressed post-operatively and expected to recover; nephrology consulted,
> ref. Dr. Menon 30/08.*

They can write that because they know **which rule fired, and on whose
authority**. They are arguing against a named guideline with a named
counter-reason. That note defends them in a review.

Now try the same against `0.87`:

> *Model output 0.87. Overridden because... ?*

There is nothing to argue with. You cannot construct a counter-argument to a
number whose reasoning is invisible. The clinician is trapped between obeying a
model they don't understand and overriding it with no defensible justification.

### The vocabulary that matters

| Term | Means |
|---|---|
| **Explainability** | you can *understand* the output |
| **Contestability** | you can *disagree with it on the record* |

**Where a human is legally accountable, contestability is the stronger
requirement.** That is why `evidence` and `source_database` are fields on the
alert and not nice-to-haves. Expanded in Ch 15.6 (the 7-field alert format).

## 4. "So we don't use embeddings?" — no, too broad

This is a real distinction worth getting exactly right.

BioPrecision-AI **does** contain learned models. The GNN research project learns
node embeddings over the Drug/Gene/Disease graph (Ch 14). There is a Random
Forest baseline in `ml/train_baseline.py`.

The rule is **not** "learned models are bad." It is:

```
  ┌──────────────────────────────────────────────────────────┐
  │  CLINICAL DECISION PATH — rules only                     │
  │  "Should this patient receive this drug?"                │
  │  decision_engine.py + Neo4j facts                        │
  │  → must be auditable, must work on rare cases            │
  └──────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐
  │  RESEARCH / RANKING PATH — learned models fine           │
  │  "Which 50 drug candidates look worth investigating?"    │
  │  GNN embeddings, Random Forest baseline                  │
  │  → a wrong ranking wastes a scientist's week,            │
  │    it does not harm a patient                            │
  └──────────────────────────────────────────────────────────┘
```

> **Learned models don't sit on the path where a wrong answer reaches a patient.**
> Same techniques, different blast radius. Formalised in 11.3.

### The complementary weakness: rules only know what's written down

A rule can only fire on interactions someone has already recorded. If a
Warfarin+Aspirin record isn't in DrugBank, `decision_engine.py` is **silent** —
not because it decided the pair is safe, but because it has never heard of it.

```
  RULES              cover only the KNOWN
  ────────           ├── high precision on what's in the book
                     └── total blindness outside it

  GNN EMBEDDINGS     propose the UNKNOWN
  ──────────────     ├── "these two drugs sit close in vector space,
                     │    they may interact"
                     └── a HYPOTHESIS, not a fact
```

That's Ch 14.8, link prediction. **But note where the output goes:** a predicted
edge goes to a *researcher*, who investigates it. It does not go to a clinician
as an alert. It becomes a rule only after a human validates it and it is
ingested into Neo4j. **Discovery and decision are two separate pipelines.**

## 5. Why every rule is a pure function

The engine:

```python
def evaluate(patient):
    alerts = []
    for rule in [renal_risk_rule, ddi_rule, contraindication_rule, polypharmacy_rule]:
        result = rule(patient)
        if result:
            alerts.append(result)
    return alerts
```

Every rule takes `patient` and returns `Alert` or `None`. **No rule returns a
modified patient. No rule reads what another rule decided.** That constraint is
deliberate.

### What breaks if a rule mutates the patient

Suppose `ddi_rule` is allowed to strip the offending drug:

```
  patient.medications = [Warfarin, Aspirin, Metformin, Atenolol, Amlodipine]   (5 drugs)
            │
            ▼
  ddi_rule   → finds Warfarin+Aspirin, removes Aspirin, fires DDI alert
            │
            ▼
  patient.medications = [Warfarin, Metformin, Atenolol, Amlodipine]            (4 drugs)
            │
            ▼
  polypharmacy_rule  →  len() >= 5 ?  NO  →  silent
                                              ▲
                                              └── the patient IS on 5 drugs.
                                                  The alert vanished because
                                                  an earlier rule edited the input.
```

The polypharmacy alert never fires and **nothing records that it was
suppressed.** A silent failure — same category as the negative-weight payload
in 11.1. Notice how this theme keeps returning.

**Verified demonstration** — the same patient, the same rules, only the order
changed:

```
ddi first    -> ['DDI_ALERT']                          final meds=4
poly first   -> ['POLYPHARMACY_ALERT', 'DDI_ALERT']    final meds=4
```

Two different clinical outputs for one patient, decided by list ordering.

### Three separate things that break

**1. Order becomes load-bearing.** Reorder the rule list, get different alerts.
Whoever wrote that list encoded clinical behaviour in what looks like arbitrary
ordering. Nobody will document it.

**2. Rules stop being independently testable.** `scripts/qa/test_02_clinical_engine.py`
can currently test `polypharmacy_rule` alone — hand it a patient, assert the
alert. With shared mutable state, testing one rule requires reproducing
everything that ran before it.

**3. The audit trail dies.** The clinician sees a DDI alert and no polypharmacy
alert. Asking *why not* requires replaying the whole sequence to discover an
earlier rule deleted a drug. Contestability — §3 — is gone.

### The correct shape

```
       patient (immutable)
              │
    ┌─────┬───┴───┬─────┬──────┐
    ▼     ▼       ▼     ▼      ▼           each rule sees the SAME patient
  renal  ddi   contra  poly  ...           none can affect another
    │     │       │     │      │           order is irrelevant
    └─────┴───┬───┴─────┴──────┘           each is testable alone
              ▼
        [alerts]  ← collected, never merged back into the input
```

**Verified:** running the engine with the rule list shuffled five times produced
identical alert sets every time, and `patient.medications` was unchanged after
evaluation.

> Pydantic validates **once** at the boundary; the rules then only **read**.
> Boundary validation and functional purity are the same instinct — establish
> facts in one place, trust them everywhere after.

## 6. When the database goes down — the most dangerous bug in the chapter

`ddi_rule` is different from the others. `renal_risk_rule` and
`polypharmacy_rule` read only fields on the patient object. `ddi_rule` must ask
Neo4j:

```python
def ddi_rule(patient, graph_service):
    for drug_a, drug_b in itertools.combinations(patient.medications, 2):
        interaction = graph_service.find_interaction(drug_a, drug_b)   # ← network call
        if interaction:
            return Alert(...)
    return None
```

Neo4j goes down mid-shift. `find_interaction()` raises a connection error.

### ❌ My first instinct was wrong

I answered that the clinician should see *"what kind of interaction hazard the
drugs produce."* But **the database is down** — the system cannot know that. It
couldn't ask. The honest state is *unknown*, not *hazardous* and not *safe*.

### ❌ The catastrophic implementation

```python
try:
    interaction = graph_service.find_interaction(drug_a, drug_b)
except ConnectionError:
    return None          # ← catastrophic
```

`None` means *"I checked, and this patient is fine."* But no check happened.

```
  Neo4j UP,   no interaction exists   →  ddi_rule returns None  →  no alert  ✓ correct
  Neo4j DOWN, interaction unknown     →  ddi_rule returns None  →  no alert  ✗ CATASTROPHIC
                                                    ▲
                                            identical output,
                                            opposite meanings
```

The clinician sees a clean screen and reasonably concludes the drugs were
checked and cleared. **An infrastructure failure has been silently converted
into a clinical all-clear.**

### ✅ What must appear on screen

```
  ┌────────────────────────────────────────────────┐
  │  ⚠  DRUG INTERACTION CHECK UNAVAILABLE         │
  │                                                │
  │  The interaction database could not be         │
  │  reached. This patient's medications have      │
  │  NOT been screened for interactions.           │
  │  Verify manually before prescribing.           │
  └────────────────────────────────────────────────┘
```

```python
def evaluate(patient, graph_service):
    alerts = []
    for rule in RULES:
        try:
            result = rule(patient, graph_service)
            if result:
                alerts.append(result)
        except ServiceUnavailable:
            alerts.append(Alert(
                risk_type="CHECK_UNAVAILABLE",
                severity="SYSTEM",
                explanation="Interaction screening could not be completed.",
                source_database="unavailable",
            ))
    return alerts
```

Three things this gets right:

1. **The unknown is visible, not converted to safe.** "I don't know" and "it's
   fine" are different answers and must look different on screen.
2. **The other rules still run.** `renal_risk_rule` needs no database — losing
   renal screening because a graph database is down would be absurd. The `try`
   wraps *each rule*, not the loop.
3. **A degraded system stays useful.** Four working checks plus honest notice
   about the fifth, rather than a blank screen or a false all-clear.

**Verified output, same patient, both states:**

```
=== Neo4j UP ===
  RENAL_RISK        | HIGH     | KDIGO 2024
  DRUG_INTERACTION  | HIGH     | DrugBank v5.1
  POLYPHARMACY      | MODERATE | AGS Beers 2023

=== Neo4j DOWN ===
  RENAL_RISK        | HIGH     | KDIGO 2024
  CHECK_UNAVAILABLE | SYSTEM   | unavailable      ← the honest answer
  POLYPHARMACY      | MODERATE | AGS Beers 2023
```

> **A system that cannot answer must say so. It must never return the answer
> that means "safe."** Absence of an alert is itself a clinical claim.

## 7. Stored facts are not trained weights

```
  TRAINED (Ch 9, 10, 14)          STORED (Ch 12 — Neo4j)
  ──────────────────────          ──────────────────────
  weights learned from labels     facts written by humans
  by gradient descent             from DrugBank / literature

  "probably dangerous, 0.87"      (Warfarin)-[:INTERACTS_WITH
                                    {severity:'HIGH',
                                     source:'DrugBank'}]->(Aspirin)
```

The Neo4j graph is a **knowledge graph** — curated facts, not a model. Warfarin +
Aspirin is in it because a pharmacologist established it and `ingest_ddi.py`
loaded that dataset. No training, no gradients, no probability.

**The rule engine reads facts. It does not infer them.**

## 8. Runnable file

```python
"""11.2 — a minimal rule engine with the three properties that matter:
   pure rules, order independence, and honest failure."""

from dataclasses import dataclass
import itertools


class ServiceUnavailable(Exception):
    pass


@dataclass(frozen=True)          # frozen=True → cannot be mutated
class Alert:
    risk_type: str
    severity: str
    explanation: str
    evidence: str = ""
    source_database: str = ""


@dataclass(frozen=True)
class Medication:
    drug_name: str
    dose_mg: float


@dataclass(frozen=True)
class Patient:
    patient_id: str
    age: int
    egfr: float
    weight_kg: float
    medications: tuple = ()      # tuple, not list → immutable


# ---------- rules: pure functions, patient in → Alert|None out ----------

def renal_risk_rule(p, graph=None):
    if p.egfr < 60 and p.age > 65:
        return Alert("RENAL_RISK", "HIGH",
                     "Reduced renal clearance in elderly patient.",
                     "KDIGO CKD stage 3 threshold (eGFR < 60)", "KDIGO 2024")
    return None


def polypharmacy_rule(p, graph=None):
    if len(p.medications) >= 5:
        return Alert("POLYPHARMACY", "MODERATE",
                     f"Patient on {len(p.medications)} concurrent medications.",
                     "Beers Criteria polypharmacy threshold", "AGS Beers 2023")
    return None


def ddi_rule(p, graph):
    for a, b in itertools.combinations(p.medications, 2):
        hit = graph.find_interaction(a.drug_name, b.drug_name)
        if hit:
            return Alert("DRUG_INTERACTION", hit["severity"],
                         f"{a.drug_name} + {b.drug_name}: {hit['effect']}",
                         hit["evidence"], hit["source"])
    return None


RULES = [renal_risk_rule, ddi_rule, polypharmacy_rule]


def evaluate(patient, graph):
    """Runs every rule. A failing rule degrades to an honest alert,
       it never degrades to silence."""
    alerts = []
    for rule in RULES:
        try:
            result = rule(patient, graph)
            if result:
                alerts.append(result)
        except ServiceUnavailable:
            alerts.append(Alert(
                "CHECK_UNAVAILABLE", "SYSTEM",
                f"{rule.__name__} could not complete. Patient NOT screened.",
                "", "unavailable"))
    return alerts


# ---------- stand-ins for graph_service.py ----------

class FakeGraph:
    DB = {("aspirin", "warfarin"): {
        "severity": "HIGH", "effect": "increased bleeding risk",
        "evidence": "DrugBank DDI record", "source": "DrugBank v5.1"}}

    def find_interaction(self, a, b):
        return self.DB.get(tuple(sorted([a.lower(), b.lower()])))


class DownGraph:
    def find_interaction(self, a, b):
        raise ServiceUnavailable("Neo4j unreachable")


if __name__ == "__main__":
    patient = Patient("P001", 72, 45, 68.0, (
        Medication("Warfarin", 5), Medication("Aspirin", 75),
        Medication("Metformin", 500), Medication("Atenolol", 25),
        Medication("Amlodipine", 5)))

    for label, graph in [("Neo4j UP", FakeGraph()), ("Neo4j DOWN", DownGraph())]:
        print(f"\n=== {label} ===")
        for a in evaluate(patient, graph):
            print(f"  {a.risk_type:18} | {a.severity:8} | {a.source_database}")
```

## 9. Never forget — carry these forward

**From this chapter, permanently:**

1. **A rule's number has an author; a model's number has a dataset.** That single
   difference produces every other difference — auditability, ease of change,
   bias immunity, and behaviour on rare cases.

2. **Rules have no sample size, so they cannot be undertrained.** They are
   strongest exactly where learned models are weakest: the rare patient, the
   rare drug. (Ties to Ch 10.3 — rare categories stay near-random.)

3. **Rules are blind outside the book.** Perfect precision on recorded facts,
   zero coverage beyond them. This is the weakness GNN link prediction addresses
   in Ch 14.8 — as a *hypothesis for a researcher*, never as an alert to a
   clinician.

4. **Contestability > explainability** wherever a human is legally accountable.
   Understanding an output isn't enough; you must be able to disagree with it on
   the record, citing what it cited.

5. **Learned models belong off the decision path.** Not "no ML in medicine" —
   ML for ranking and discovery, rules for anything whose wrong answer reaches
   a patient. (Formalised next, in 11.3.)

6. **Pure functions: same input → same output, no side effects.** The moment one
   rule can edit shared state, order becomes load-bearing, isolated tests become
   impossible, and alerts vanish without a trace.

7. **A system that cannot answer must say so — never return the answer that
   means "safe."** "Unknown" and "fine" must never share a representation.
   Absence of an alert is itself a clinical claim.

8. **Wrap the `try` around each rule, not the loop.** One failing dependency
   must not take down checks that never needed it.

**The through-line of Chapter 11 so far:**

```
  11.1  bad data must fail LOUDLY at the boundary
  11.2  a broken dependency must fail LOUDLY at the rule
        └── same principle, different layer:
            silence is the most dangerous output a safety system can produce
```
