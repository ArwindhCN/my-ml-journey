## The core idea in one line

**Validate once at the door, not everywhere downstream.**

`patient.py` is not a file of data containers. It is *the door*.

## 1. The problem — an endpoint with no validation

```python
@app.post("/api/analyze")
def analyze(payload: dict):
    age  = payload["age"]
    egfr = payload["egfr"]

    if egfr < 60 and age > 65:
        return {"alert": "RENAL_RISK", "severity": "HIGH"}
    return {"alert": None}
```

```
   EHR / lab system                FastAPI endpoint              Clinician's screen
   ────────────────                ────────────────              ─────────────────
        payload  ───────────────►   payload["age"]     ───────►   alert / no alert
        (a dict)                    payload["egfr"]
                                    egfr < 60 and age > 65
                                    ▲
                                    │
                              nothing checks
                              what arrived here
```

### Three malformed payloads

| | Payload | Fault |
|---|---|---|
| **A** | `{"age": "67", "egfr": 45}` | `age` is a string — EHR exported it as text |
| **B** | `{"age": 67}` | `egfr` missing — lab result hadn't returned |
| **C** | `{"age": 67, "egfr": 45, "weight_kg": -78.5}` | data-entry sign error |

**Observed behaviour (verified):**

```
A -> TypeError : '>' not supported between instances of 'str' and 'int'
B -> KeyError  : 'egfr'
C -> RENAL_RISK          ← runs to completion, returns 200 OK
```

### Why A crashes

```
    if egfr < 60 and age > 65:
       ───┬────       ───┬───
          │              │
          │              └─► "67" > 65  →  str > int
          │                  ✗ TypeError — Python 3 will not order
          │                    a string against an integer
          │
          └─► 45 < 60 → True, so `and` does NOT short-circuit;
                        the right-hand side IS evaluated
```

**Near-miss worth noting:** `and` short-circuits. If `egfr` had been `70`, the
left side is `False`, `age > 65` is never evaluated, and the string `"67"`
sails through with no error at all.

```
verified: analyze_raw({"age": "67", "egfr": 70})  ->  None
```

### Vocabulary correction I needed

| Access form | Missing → raises |
|---|---|
| `payload["egfr"]` — dict, square brackets | **`KeyError`** |
| `obj.egfr` — attribute, dot access | `AttributeError` |

Case B is a `KeyError`, not an attribute error. This matters because Pydantic
moves us from the first form to the second.

## 2. Which is most dangerous — and why

```
A  →  500 Internal Server Error   →  clinician sees:  ✗ something broke
B  →  500 Internal Server Error   →  clinician sees:  ✗ something broke
C  →  200 OK                      →  clinician sees:  ⚠ RENAL_RISK, HIGH
                                                      (looks completely normal)
```

**C is the most dangerous — but not because `-78.5` is an impossible weight.**
All three payloads contain bad data. What separates C is that **the
impossibility passed through undetected.**

A and B *announce themselves*: a log fills, someone is paged, the request is
retried. The bad data never reaches a decision. C produces a clean `200` and a
plausible alert. Nothing in the system knows anything went wrong.

> **Theme of Chapter 11: loud failures are safer than silent ones.**
> A crash is visible. A wrong number that looks plausible reaches a clinician.

### The distance problem

`weight_kg` is never read by *this* endpoint. But the payload becomes a
`Patient`, which reaches `decision_engine.py`, which has a weight-based dosing
rule:

```
dose = 5 mg/kg × weight_kg

   weight =  78.5  →  dose =  392.5 mg     ✓ plausible
   weight = -78.5  →  dose = -392.5 mg     ✗ meaningless
```

A negative dose is not a wrong dose — it is a non-existent quantity. There is
no such thing as administering minus 392 milligrams.

**Correction to my wording:** the relationship is not *inverted* (that would be
`1/x`, a reciprocal). It is **sign-flipped** — direct proportionality keeps its
shape and flips its sign.

```
  EHR export          FastAPI          Patient        decision_engine      alert JSON       clinician
  ──────────          ───────          ───────        ───────────────      ──────────       ─────────
   -78.5      ───►     accepted  ───►  stored   ───►   -392.5 mg     ───►   rendered  ───►   reads it
      │                                                                                          │
      └──────────────────────── error travels this entire distance ─────────────────────────────┘
             ▲                                                                        ▲
        entered here                                                          noticed here (maybe)
```

**Why silent failures are expensive:** the gap between where a bug *enters* and
where it *surfaces*. Whoever investigates starts debugging `decision_engine.py`,
because that's where the strange number appeared. The actual fault was in a CSV
export, hours earlier, in a different system.

A `KeyError` (case B) names the exact line and the exact key. Case C tells you
nothing, late, in the wrong file.

## 3. Why not just guard inside every function?

```
                    payload (unvalidated)
                            │
        ┌───────────┬───────┴───────┬───────────┬───────────┐
        ▼           ▼               ▼           ▼           ▼
   ddi_rule()  contra_rule()  polypharm()  dose_calc()  graph_query()
   ┌────────┐  ┌──────────┐   ┌────────┐   ┌────────┐   ┌─────────┐
   │ check  │  │  check   │   │ check  │   │ check  │   │  check  │
   │ weight │  │  weight  │   │ weight │   │ weight │   │   ???   │
   └────────┘  └──────────┘   └────────┘   └────────┘   └─────────┘
```

The eleventh function is safe **only if the developer remembers to add the
guard.** Nothing forces them. Forgetting produces no error — it produces a
function that silently accepts a negative weight. Correctness becomes a property
of *human memory* rather than a property of the *system*.

Four concrete failure modes:

```
1. COVERAGE      10 functions guard, 1 forgets → that one is the hole.
                 Safety = the weakest function, not the strongest.

2. DRIFT         ddi_rule():   weight > 0
                 dose_calc():  weight > 0 and weight < 500
                 → two functions disagree on what "valid" means.

3. CHANGE COST   New rule: age must be 0–120 → edit 10 files.
                 Miss one → back to problem 1.

4. LATE DETECTION  Even when a guard fires, it fires deep in the call stack,
                   long after the bad data entered.
```

**The alternative:** check *once*, at the moment data crosses from the outside
world into the system. If nothing invalid can get in, nothing downstream needs
to defend itself. `dose_calc()` can trust `patient.weight_kg` is positive
because that was established before the object existed.

## 4. What is actually on the wire

HTTP does not transmit Python objects. It transmits **bytes of text.**

```
POST /api/analyze HTTP/1.1
Content-Type: application/json

{"age": "67", "egfr": 45, "weight_kg": 78.5}
   ▲
   └── every one of these characters is just text.
       There is no "int" or "str" out here. Only bytes.
```

```
  EHR ──► bytes ──► json.loads() ──► Python dict ──► Pydantic ──► Patient object
                         │                              │
                    types appear                   types checked
                    for the first time             against the model
```

This is why it's called **parsing**, not merely checking. Pydantic sits exactly
on the boundary between "text on the wire" and "typed Python object."

## 5. Layer one — type annotations

```python
from pydantic import BaseModel

class PatientV1(BaseModel):
    age:       int
    egfr:      float
    weight_kg: float
```

```python
@app.post("/api/analyze")
def analyze(patient: PatientV1):
    if patient.egfr < 60 and patient.age > 65:
        return {"alert": "RENAL_RISK"}
```

### Lax mode — Pydantic *coerces* before it rejects

```
verified:
  PatientV1(age="67", egfr=45, weight_kg=78.5)
    -> age=67 egfr=45.0 weight_kg=78.5
          ▲
          └── an int. The string "67" was CONVERTED, not rejected.
```

By default Pydantic runs in **lax mode**: if a value can be sensibly converted
to the declared type, it converts it. Only an unparseable value fails:

```
verified:
  PatientV1(age="sixty-seven", ...)
    -> int_parsing: Input should be a valid integer,
                    unable to parse string as an integer
```

**Consequence:** the EHR's text-export problem is silently *fixed* at the door.
The `TypeError` from case A can no longer happen — not because it's caught, but
because the condition that caused it no longer exists past the boundary.

### What types do NOT protect against

```
verified:
  PatientV1(age=67, egfr=45, weight_kg=-78.5)
    -> age=67 egfr=45.0 weight_kg=-78.5      ← ACCEPTED
```

```
  {"weight_kg": -78.5}
          │
          ▼
  ┌───────────────────────────────┐
  │  Is it a float?               │   ← TYPE     ✓ passes
  │  Is it a possible weight?     │   ← VALUE    ✗ nothing asked this
  └───────────────────────────────┘
```

A type says what **kind** of thing a field holds. It says nothing about which
values of that kind make sense. `float` covers `-78.5`, `0.0`, `1e9` and `78.5`
equally — the type system has no opinion on human anatomy.

**Types close the A and B holes completely and leave C wide open.**

## 6. Layer two — `Field` value constraints

```python
from pydantic import BaseModel, Field

class PatientV2(BaseModel):
    age:       int   = Field(..., ge=0, le=120)
    egfr:      float = Field(..., ge=0, le=200)
    weight_kg: float = Field(..., gt=0, le=500)
```

| Operator | Meaning |
|---|---|
| `ge` | greater than or equal |
| `gt` | strictly greater than |
| `le` | less than or equal |
| `...` | required — no default |

### `ge=0` for age but `gt=0` for weight

```
  age:       ge=0   →  [0 .......... 120]   0 is INSIDE  (a newborn)
  weight_kg: gt=0   →  (0 .......... 500]   0 is OUTSIDE (impossible)
                        ▲
                        └── one character of difference,
                            and one of them silently excludes real infants
```

A neonate genuinely *is* `age = 0` — a real patient, not bad data. No patient
has ever weighed zero kilograms; zero weight is a broken record.

**Note the asymmetry of the two mistakes:**

| Mistake | Result | Failure type |
|---|---|---|
| `ge` on weight instead of `gt` | zero passes through | **silent** — reaches clinician |
| `gt` on age instead of `ge` | newborn gets a 422 | **loud** — visible immediately |

Both are bugs, but only one reaches a clinician disguised as an answer. Be
fussy in the silent direction.

### Case C finally dies at the door

```
verified:
  PatientV2(age=67, egfr=45, weight_kg=-78.5)
    -> ('weight_kg',)  "Input should be greater than 0"  input=-78.5
```

```
  422 Unprocessable Entity
  {
    "loc":   ["body", "weight_kg"],
    "msg":   "Input should be greater than 0",
    "input": -78.5
  }
```

Compare with the original chain — `-392.5 mg` surfacing five layers later in the
wrong file. Here the error names the exact field, the exact rule and the
offending value **before a single clinical rule executes.** The gap between
where the bug entered and where it was caught has collapsed to zero.

```
verified: PatientV2(age=0, egfr=90, weight_kg=3.2)  ->  accepted (newborn)
```

## 7. Layer three — validators

Some rules cannot be expressed as a constraint on one field. Example: *a
medication list must not contain the same drug twice.*

```
  gt=0  ────────────────►  looks at ONE value, in isolation
                           weight_kg = -78.5
                           ▲
                           └── needs nothing else to decide

  no duplicates  ────────►  looks at a value RELATIVE TO OTHER VALUES
                            medications = [Warfarin, Aspirin, Warfarin]
                                            ▲                    ▲
                                            └────────────────────┘
                                            neither entry is invalid alone;
                                            the invalidity lives BETWEEN them
```

**Why `Field(...)` cannot express it:** a field constraint is evaluated
per-field with no access to anything else on the model. Ask it about
`Warfarin` and it cannot answer — Warfarin is a fine drug name. The violation
only exists when you can see the *whole list at once*.

It is **not that the check is more complicated — it is that it needs a wider
scope** than a field constraint has.

```python
from pydantic import BaseModel, Field, field_validator

class Medication(BaseModel):
    drug_name: str
    dose_mg:   float = Field(..., gt=0)

class Patient(BaseModel):
    patient_id:  str
    age:         int   = Field(..., ge=0, le=120)
    egfr:        float = Field(..., ge=0, le=200)
    weight_kg:   float = Field(..., gt=0, le=500)
    medications: list[Medication] = []

    @field_validator("medications")
    @classmethod
    def no_duplicate_drugs(cls, meds):
        names = [m.drug_name.strip().lower() for m in meds]
        if len(names) != len(set(names)):
            raise ValueError("duplicate drug in medication list")
        return meds
```

```
verified:
  Warfarin + Aspirin           -> accepted
  Warfarin + warfarin          -> "Value error, duplicate drug in medication list"
```

Note `.strip().lower()` — `"Warfarin"` and `"warfarin"` are the same drug.
Normalise before comparing.

**DSA link:** `len(names) != len(set(names))` is the standard duplicate-detection
idiom — a set discards repeats, so a shrunk length means a repeat existed.
O(n) time, O(n) space. This comes back in LeetCode array problems.

### The three widening scopes

```
   TYPE          int / float / str / list[Medication]      one field, kind only
      ▼
   FIELD         Field(gt=0, le=500)                       one field, value range
      ▼
   VALIDATOR     @field_validator                          across a collection
```

## 8. What does NOT belong in a validator

BioPrecision-AI's DDI rule — Warfarin + Aspirin is dangerous together — is
**not** a Pydantic concern.

### Correction: nothing here is trained

```
  TRAINED (Ch 9, 10, 14)          STORED (Ch 12 — Neo4j)
  ──────────────────────          ──────────────────────
  weights learned from labels     facts written by humans
  by gradient descent             from DrugBank / literature

  "probably dangerous, 0.87"      (Warfarin)-[:INTERACTS_WITH
                                    {severity:'HIGH',
                                     source:'DrugBank'}]->(Aspirin)
```

The Neo4j graph is a **knowledge graph** — curated facts, not a model. Warfarin
+ Aspirin is in there because a pharmacologist established it and `ingest_ddi.py`
loaded that dataset. No training, no gradients, no probability. This is exactly
the distinction taught in **11.3 — Symbolic AI vs Statistical AI**, and it is
why BioPrecision-AI uses rules for clinical decisions.

### Three reasons the DDI check stays out of the model

```
  no_duplicate_drugs          →  needs: the payload
                                 answer: instant, offline, permanent

  warfarin + aspirin = risk   →  needs: the payload  +  Neo4j
                                          ▲
                                          └── a network call to an external
                                              database that can be slow, down,
                                              or updated tomorrow
```

1. **A DDI is not invalid data.** The patient really *is* on both drugs. That
   payload is *correct*. A 422 would be a lie — and would delete the exact case
   the system exists to detect.
2. **The right output is different.** Bad data gets a rejection. A DDI gets a
   rich alert: `{drug, risk_type, severity, evidence, source_database,
   explanation}` (the 7-field format, Ch 15.6). A validator can only raise or
   return; it cannot produce an alert.
3. **Neo4j downtime would become a validation failure.** The door would stop
   accepting patients because a database was unreachable.

### The architecture

```
  payload ──► Pydantic ──► Patient ──► decision_engine.py ──► alerts
              ═════════     (trusted)   ═════════════════
              is it              │      is it dangerous?
              well-formed?       │      (queries Neo4j)
                                 │
                       everything past here can
                       assume the data is sane
```

**This is why `decision_engine.py` contains no defensive `if weight <= 0`
checks. It does not need them. `patient.py` already guaranteed it.**

```python
def calculate_dose(patient, mg_per_kg):
    return mg_per_kg * patient.weight_kg     # no guard needed

verified: calculate_dose(patient, 5)  ->  340.0 mg
```

## 9. Runnable file

```python
from pydantic import BaseModel, Field, field_validator, ValidationError


class Medication(BaseModel):
    drug_name: str
    dose_mg:   float = Field(..., gt=0)


class Patient(BaseModel):
    patient_id:  str
    age:         int   = Field(..., ge=0,  le=120)
    egfr:        float = Field(..., ge=0,  le=200)
    weight_kg:   float = Field(..., gt=0,  le=500)
    medications: list[Medication] = []

    @field_validator("medications")
    @classmethod
    def no_duplicate_drugs(cls, meds):
        names = [m.drug_name.strip().lower() for m in meds]
        if len(names) != len(set(names)):
            raise ValueError("duplicate drug in medication list")
        return meds


def calculate_dose(patient: Patient, mg_per_kg: float) -> float:
    """No defensive checks. weight_kg is guaranteed positive by the model."""
    return mg_per_kg * patient.weight_kg


if __name__ == "__main__":
    p = Patient(
        patient_id="P001", age=72, egfr=45, weight_kg=68.0,
        medications=[
            {"drug_name": "Warfarin", "dose_mg": 5},
            {"drug_name": "Aspirin",  "dose_mg": 75},
        ],
    )
    print(p.patient_id, calculate_dose(p, 5), "mg")

    for bad in [
        {"patient_id": "P002", "age": 67, "egfr": 45, "weight_kg": -78.5},
        {"patient_id": "P003", "age": 67, "weight_kg": 70.0},
        {"patient_id": "P004", "age": 72, "egfr": 45, "weight_kg": 68.0,
         "medications": [{"drug_name": "Warfarin", "dose_mg": 5},
                         {"drug_name": "warfarin", "dose_mg": 2}]},
    ]:
        try:
            Patient(**bad)
        except ValidationError as e:
            err = e.errors()[0]
            print(err["loc"], "->", err["msg"])
```

## 10. Summary table

| Layer | Catches | Example | Cannot catch |
|---|---|---|---|
| **Type** | wrong *kind* of data | `"sixty-seven"` for `age` | `-78.5` as a weight |
| **`Field`** | impossible *values* | `weight_kg = -78.5` | duplicate drugs |
| **`@field_validator`** | invalid *combinations* | Warfarin listed twice | DDI risk (needs Neo4j) |
| **Rule engine** | dangerous *situations* | Warfarin + Aspirin | — |
