## The core idea in one line

**`await` doesn't make anything faster — it marks the one place where your code
is allowed to step aside so someone else can run.**

---

## 1. Where the time actually goes

```python
def ddi_rule(patient, graph_service):
    for drug_a, drug_b in itertools.combinations(patient.medications, 2):
        interaction = graph_service.find_interaction(drug_a, drug_b)
        if interaction:
            return Alert(...)
    return None
```

5 medications → 10 drug pairs. Each `find_interaction()` is a network round trip
to Neo4j. Say 40ms each.

```
  pair 1   ├──40ms──┤
  pair 2            ├──40ms──┤
  pair 3                     ├──40ms──┤
  ...                                  ...
  pair 10                                        ├──40ms──┤
           └──────────────── 400ms total ────────────────┘
```

Break one 40ms round trip down:

```
   ├─ 0.1ms ─┤├──────────── 39.8ms ────────────┤├─ 0.1ms ─┤
   build the   waiting for the network and Neo4j   parse the
   query       (CPU has nothing to do)             response
```

**~99.5% of that time is waiting.** The CPU is idle, parked on a socket.

---

## 2. Occupancy is not utilisation

A second nurse submits an analysis at another terminal while patient one is
mid-lookup. With synchronous code, she waits.

The precise wording matters: the server thread isn't "fetching" — it is
**blocked**. The network card and Neo4j do the fetching. The thread sits still,
holding its seat:

```
  CPU busy:      0.2ms  ████
  Thread held:  40.0ms  ████████████████████████████████████████
                        ▲
                        └── 39.8ms of that is a thread occupying a
                            worker slot purely to sit still
```

> **Occupancy is not utilisation.** Your server can be completely full while the
> CPU is nearly idle.

Scale it. A worker handles one request at a time; run 4 workers:

```
  4 workers × 1 request each  =  4 concurrent patients

  patient 5 onward:  queued
  patient 20:        waits ~1.6 seconds before its own 400ms even starts
```

An OP ward at peak hour has more than four terminals. The server refuses work
not because it is out of CPU — it has nearly all of it free — but because every
worker is parked on a socket. **You would scale this system by buying more
machines to run more idle threads.**

## 3. What `async` actually is

```python
async def ddi_rule(patient, graph_service):
    for drug_a, drug_b in itertools.combinations(patient.medications, 2):
        interaction = await graph_service.find_interaction(drug_a, drug_b)
        if interaction:
            return Alert(...)
    return None
```

### First — the three words this chapter runs on

Everything below is unreadable without these. Define them properly.

**BLOCKING** — an ordinary function that does not return until its work is done.
While it runs, the thread executing it can do nothing else.

```python
def blocking_lookup(a, b):
    time.sleep(0.04)          # thread is stuck here for 40ms
    return result
```

Nothing is wrong with this code — it is how almost all Python is written. The
word only describes the fact that **the thread is occupied for the entire
duration**, even though 39.8ms of it is spent waiting on a network rather than
computing. The real Neo4j driver, `requests.get()`, `open().read()`,
`time.sleep()` — all blocking.

**ASYNC** — a function declared `async def`, which is *allowed* to pause partway
through and let the thread go do something else.

```python
async def async_lookup(a, b):
    await asyncio.sleep(0.04)     # pauses HERE, releases the thread
    return result
```

The difference is the word `await`. That is not decoration — it is the
mechanism.

**YIELD** — to voluntarily hand the thread back so other work can run.

Same everyday meaning as the traffic sign. At a junction, *yield* doesn't mean
stop permanently; it means let others through, then continue. Identical here:
the function pauses, others run, it resumes where it left off.

```
  blocking:  ████████████████████████  thread held the whole time
  async:     ██░░░░░░░░░░░░░░░░░░░░██  ░ = yielded, thread free for others
               ▲                    ▲
             await                resume
```

> **Only `await` yields. There is no other way.** A function with no `await`
> inside it never yields, no matter what keywords are written on it.

### The event loop — one thread

This is the piece that has to be understood before anything else makes sense.
**The event loop is a single thread.** Not a pool, not a manager delegating to
helpers. One thread running one loop, doing one thing at a time:

```
  ┌─► pick a ready task
  │   run it until it hits an `await`
  │   park it, note what it's waiting for
  │   pick the next ready task
  └───────────────────────────────┘
```

Every user on the server is a task in that one loop.

> **The only way a task gives up control is by hitting an `await`.** No timer, no
> interrupt, nothing can pause a task from outside. The loop cannot take control
> back — a task must hand it over voluntarily.

```
  async task:   run ──► await ──► [loop runs others] ──► resume
                              ▲
                              └── the ONLY door out
```

### What this buys

```
  WITHOUT async                      WITH async
  ─────────────                      ──────────
  nurse 1  ████████████████          nurse 1  ██░░██░░██░░██
  nurse 2  ................████      nurse 2  ░░██░░██░░██░░
           ▲                                  ▲
     blocked, waiting her turn         interleaved in the gaps
                                       ░ = suspended at an await
```

**Verified — two users, three lookups each:**

```
  async driver (yields)      wall= 120.7ms  per-nurse=['121ms', '121ms']
  blocking driver            wall= 241.3ms  per-nurse=['121ms', '121ms']
```

With yielding, two users finish in the time of one. Without, they queue.

## 4. ❌ Why `await` did nothing for nurse 1's own request

My answer was that nurse 1 "can't get two drugs at the same time because the
server is given to her, so it switches between nurses." That implies an
**external scheduler is rationing her**. It isn't. Nothing is stopping her — the
limitation is in her own code.

```python
for drug_a, drug_b in pairs:
    interaction = await graph_service.find_interaction(drug_a, drug_b)
                  ▲
                  └── "pause here until THIS one comes back,
                       then continue to the next line"
```

Pair 2's query isn't sent while pair 1 is in flight. It isn't sent until pair 1
has **fully returned**. The queries were written as a sequence, so they run as a
sequence.

> **`await` does not create parallelism. It creates a *yield point*** — a place
> where the event loop may run someone else's code while you're stuck.

```
  nurse 1's own timeline, unchanged:

  pair1 ──await──► pair2 ──await──► pair3 ──await──► ... 400ms
        ▲
        └── the ░ gaps are given away to OTHERS,
            never used by nurse 1 herself
```

## 5. `asyncio.gather` — overlapping your own waits

```python
async def ddi_rule(patient, graph_service):
    pairs = list(itertools.combinations(patient.medications, 2))

    results = await asyncio.gather(*[
        graph_service.find_interaction(a, b) for a, b in pairs
    ])

    return [make_alert(p) for p, hit in zip(pairs, results) if hit]
```

```
  SEQUENTIAL awaits                 asyncio.gather
  ─────────────────                 ──────────────
  pair 1  ├─40─┤                    pair 1  ├─40─┤
  pair 2       ├─40─┤               pair 2  ├─40─┤
  pair 3            ├─40─┤          pair 3  ├─40─┤
  ...                    ...        ...     ├─40─┤
  pair 10                    ├─40─┤ pair 10 ├─40─┤
          └──── 400ms ────┘                 └─40ms─┘
```

All ten queries go out, then you wait **once** for all of them. The ten waits
happen *on top of each other* instead of end to end.

> **`await` immediately = sequential. Collect the coroutines first, then
> `gather` = concurrent.**

## 6. The early `return` is a clinical bug

The 11.2 loop returns on the **first** interaction found. But a patient on five
drugs can have several interacting pairs.

**Verified — same patient, two real interactions present:**

```
  sequential + early return     40.4ms   hits=1  [(Warfarin, Aspirin)]
  sequential, all pairs        402.3ms   hits=2  [(Warfarin, Aspirin), (Warfarin, Atenolol)]
  asyncio.gather                40.6ms   hits=2  [(Warfarin, Aspirin), (Warfarin, Atenolol)]
```

The early-return version is fast **and wrong**. It reports one interaction and
never queries the rest:

```
  Warfarin + Aspirin      → HIGH, found first  → RETURNED
  Warfarin + Atenolol     → MODERATE           → never queried
  Metformin + Amlodipine  → MODERATE           → never queried
                                                 ▲
                                                 └── the clinician is told about
                                                     one problem and never learns
                                                     of the others
```

The clinician removes Aspirin, re-runs, and *now* discovers a second
interaction. Two rounds of work — and in between, they believed the patient was
clear. **A silent omission, the same family of bug as everything else in this
chapter.**

### ⚠️ Wording correction

I described the early exit as *"even if one goes wrong it will return."* It
returns when one is **found** — the search *succeeded*. Nothing went wrong. It's
an early exit on success, not on error. "Goes wrong" points at exception
handling, a different topic.

### The trade-off

| | Sequential + early return | `gather` |
|---|---|---|
| Best case latency | 40ms (hit on pair 1) | 40ms |
| Worst case latency | 400ms (no hits) | 40ms |
| Queries sent | 1 to 10 | always 10 |
| **Finds all interactions** | **no** | **yes** |
| Load on Neo4j | lower | higher, bursty |

**For a clinical rule, completeness beats query economy.** Ten cached lookups
cost Neo4j almost nothing; a missed moderate interaction costs a patient. The
early-exit pattern belongs where you genuinely need only the first match — an
existence check, a permission lookup, a cache probe.

Note the shape change `gather` forces: the rule can no longer return
`Alert | None`, it must return `list[Alert]`. Which is exactly what 11.4's
`AnalysisResponse.alerts` was already typed as. **The contract was ahead of the
engine.**

## 7. The trap: a blocking call inside `async def`

```python
async def ddi_rule(patient, graph_service):
    results = await asyncio.gather(*[
        graph_service.find_interaction(a, b)   # ← sync driver, NOT a coroutine
        for a, b in pairs
    ])
```

`find_interaction()` is an ordinary synchronous function. It sits on a socket
for 40ms. It contains no `await`, because it was never written as a coroutine.

### First failure: `gather` silently stops working

```
  gather over ASYNC lookups        gather over BLOCKING lookups
  ─────────────────────────        ────────────────────────────
  pair 1  ├─40─┤                   pair 1  ├─40─┤
  pair 2  ├─40─┤                   pair 2       ├─40─┤
  pair 3  ├─40─┤                   pair 3            ├─40─┤
          └─40ms─┘                                        └── 400ms
```

**Left:** each lookup hits `await`, yields, and the thread immediately starts the
next one. All ten wait simultaneously. ≈ 40ms.

**Right:** each lookup never yields, so the thread is stuck inside lookup 1 until
it finishes. Only then can lookup 2 begin. 400ms — identical to the plain
sequential loop.

> **`gather` does not create the overlap. It only exploits overlap that `await`
> makes possible.** Given blocking functions, it has nothing to interleave and
> silently degrades to sequential — no error, no warning.

### Second failure: the whole server stops

**The loop has one thread. That thread is now inside a function that will not
return for 40ms and will never yield.** So during those 40ms the event loop can
run *nothing*:

```
  the one thread:  ████████████████ blocked in find_interaction() ███████████████

  nurse 2's request        ⏸ frozen
  a health check           ⏸ frozen
  a login                  ⏸ frozen
  a patient list refresh   ⏸ frozen
  every other user         ⏸ frozen
```

### ⚠️ What exactly is "worse" here — a comparison I first stated ambiguously

**The comparison is NOT `gather` vs sequential.** `gather` is not what made
anything worse; adding `async def` did. The two things being compared are two
versions of the whole endpoint, both using the same blocking driver:

```
  version 1:  def analyze(...)         + blocking Neo4j driver
  version 2:  async def analyze(...)   + blocking Neo4j driver     ← worse
```

Why version 2 loses:

```
  sync def  + blocking driver
  ───────────────────────────
  worker 1  ████ patient A, 400ms ████
  worker 2  ████ patient B, 400ms ████        ← unaffected
  worker 3  ████ patient C, 400ms ████        ← unaffected
  worker 4  ████ patient D, 400ms ████        ← unaffected
            4 patients at once. Slow, but the server works.

  async def + blocking driver
  ───────────────────────────
  the one loop thread  ████ patient A, 400ms ████
  everyone else        ⏸ frozen ⏸ frozen ⏸ frozen
            1 patient at a time. The server is dead while A runs.
```

A regular `def` FastAPI endpoint gets its **own worker thread per request**, so
blocking one leaves the others running. That isolation is free — you never asked
for it. Writing `async def` moves the endpoint onto the single-threaded event
loop, where blocking it blocks *everyone*.

**Four concurrent patients become one.** Throughput drops 4× from adding a
keyword that was meant to help.

```
  sync def   + blocking driver  →  one worker blocked, others fine
  async def  + blocking driver  →  THE WHOLE SERVER STOPS      ← worst of both
  async def  + async driver     →  what you actually wanted
```

### The sentence, phrase by phrase

> *"`async def` is only a win if everything inside it yields. Adding `async`
> while keeping a blocking driver doesn't get you partway there — it takes away
> the thread-per-request safety net and gives nothing back."*

| Phrase | Meaning |
|---|---|
| **"only a win if everything inside it yields"** | `async def` makes nothing faster by itself. The entire benefit comes from `await`s inside releasing the thread. |
| **"doesn't get you partway there"** | You'd expect a half-measure to give half the benefit. It gives **none**. Either the function releases the thread or it doesn't — no partial credit. |
| **"the thread-per-request safety net"** | What you lose: a regular `def` endpoint gets its own worker thread, so a stuck request can't affect the others. Free isolation. |
| **"gives nothing back"** | You traded that isolation for the *ability* to yield. If your code can't yield, you paid and received nothing. |

| | isolation | yielding |
|---|---|---|
| `sync def` + blocking driver | ✅ own thread per request | ❌ |
| `async def` + blocking driver | ❌ shared loop thread | ❌ ← **worst** |
| `async def` + async driver | ❌ shared loop thread | ✅ ← works |

**Row 2 has neither property.** That is the whole warning.

### The two fixes

```python
# 1. use a driver that is actually async
from neo4j import AsyncGraphDatabase
result = await session.run(query)          # a real coroutine, a real yield point

# 2. or push the blocking call off the loop's thread
result = await asyncio.to_thread(graph_service.find_interaction, a, b)
```

`to_thread` hands blocking work to a separate thread and gives the loop an
`await` to park on — the escape hatch for libraries with no async version.

**Verified** — `gather` + `to_thread` over the blocking driver: **86.1ms** vs
402.3ms sequential. Not as good as native async (40.6ms), because the thread
pool has its own overhead and limits, but far better than freezing the loop.

> **`async` is not a speed-up you sprinkle on. It is a contract that every wait
> inside the function is awaited.** One blocking call anywhere in the chain — a
> sync DB driver, `requests.get`, `time.sleep`, a heavy CPU loop — voids it.

## 8. Runnable file

```python
"""11.5 — measure the difference yourself.
   Simulates a 40ms Neo4j round trip with asyncio.sleep (yields)
   and time.sleep (blocks)."""

import asyncio
import time
import itertools

MEDS = ["Warfarin", "Aspirin", "Metformin", "Atenolol", "Amlodipine"]
PAIRS = list(itertools.combinations(MEDS, 2))
DDI = {("aspirin", "warfarin"), ("atenolol", "warfarin")}
LATENCY = 0.04


def key(a, b):
    return tuple(sorted([a.lower(), b.lower()]))


async def async_lookup(a, b):
    await asyncio.sleep(LATENCY)          # a real yield point
    return key(a, b) in DDI


def blocking_lookup(a, b):
    time.sleep(LATENCY)                    # blocks the whole thread
    return key(a, b) in DDI


async def sequential_early():
    """The 11.2 shape. Fast, and clinically incomplete."""
    for a, b in PAIRS:
        if await async_lookup(a, b):
            return [(a, b)]
    return []


async def sequential_all():
    """Complete, but pays every wait end to end."""
    hits = []
    for a, b in PAIRS:
        if await async_lookup(a, b):
            hits.append((a, b))
    return hits


async def gathered():
    """Complete AND fast: all waits overlap."""
    res = await asyncio.gather(*[async_lookup(a, b) for a, b in PAIRS])
    return [p for p, hit in zip(PAIRS, res) if hit]


async def gathered_blocking():
    """Blocking driver, kept off the event loop's thread."""
    res = await asyncio.gather(
        *[asyncio.to_thread(blocking_lookup, a, b) for a, b in PAIRS])
    return [p for p, hit in zip(PAIRS, res) if hit]


async def timed(name, fn):
    t = time.perf_counter()
    out = await fn()
    print(f"  {name:32} {(time.perf_counter()-t)*1000:7.1f}ms  hits={len(out)}")


async def two_users():
    """Shows the loop freezing when a task refuses to yield."""
    async def nurse(blocking):
        for _ in range(3):
            if blocking:
                time.sleep(LATENCY)        # never yields
            else:
                await asyncio.sleep(LATENCY)

    for label, blocking in [("async driver (yields)", False),
                            ("blocking driver", True)]:
        t = time.perf_counter()
        await asyncio.gather(nurse(blocking), nurse(blocking))
        print(f"  {label:26} wall={(time.perf_counter()-t)*1000:7.1f}ms")


async def main():
    print(f"{len(PAIRS)} pairs, {LATENCY*1000:.0f}ms each, "
          f"{len(DDI)} real interactions\n")
    print("=== one patient's own lookups ===")
    await timed("sequential + early return", sequential_early)
    await timed("sequential, all pairs", sequential_all)
    await timed("asyncio.gather", gathered)
    await timed("gather + to_thread", gathered_blocking)
    print("\n=== two users sharing one event loop ===")
    await two_users()


if __name__ == "__main__":
    asyncio.run(main())
```

## 9. Never forget — carry these forward

1. **Almost all of an I/O call is waiting.** 39.8ms of a 40ms database round trip
   uses no CPU at all. Concurrency exists to reclaim that time.

2. **Occupancy is not utilisation.** A full server with an idle CPU is the normal
   failure mode of blocking I/O — and adding machines is the expensive way to fix
   the wrong problem.

3. **The event loop is ONE thread.** Every user is a task in it. This single fact
   explains every other rule here.

4. **A task only yields at an `await`.** Nothing can preempt it from outside. The
   loop cannot take control back.

5. **`await` is a yield point, not parallelism.** Sequential `await`s in a loop
   stay sequential — the gaps are given to *other* users, never to yourself.

6. **Collect coroutines, then `gather`, to overlap your own waits.** 400ms → 40ms
   for ten independent lookups.

7. **An early `return` on the first match is a silent omission** when the caller
   needs every match. Fast and incomplete is not a trade-off worth taking in a
   clinical rule.

8. **A blocking call inside `async def` freezes the entire server** — every user,
   not just the current request. `async def` + a blocking driver is worse than
   plain `def` + a blocking driver, because `def` gives every request its own
   worker thread and `async def` takes that away. Four concurrent patients
   become one.

8b. **`gather` over blocking calls silently degrades to sequential.** It has
   nothing to interleave, so it runs them one by one — no error, no warning,
   no speed-up. `gather` exploits overlap that `await` creates; it does not
   create overlap itself.

9. **`asyncio.to_thread` is the escape hatch** for libraries with no async
   version. Slower than native async, vastly better than blocking the loop.

10. **`async` is a promise, not an optimisation.** Every wait inside the function
    must be awaited or the promise is void.
