## The core idea in one line

**A response model is not validation — it is a promise. It protects the people
consuming your API from your own future mistakes.**

---

## 1. The setup

The rule engine produces an alert, serialized and sent over the network:

```json
{
  "risk_type": "DRUG_INTERACTION",
  "severity": "HIGH",
  "explanation": "Warfarin + Aspirin: increased bleeding risk",
  "evidence": "DrugBank DDI record",
  "source_database": "DrugBank v5.1"
}
```

The React frontend renders it:

```jsx
<AlertCard>
  <Badge color={sevColor(alert.severity)}>{alert.severity}</Badge>
  <p>{alert.explanation}</p>
  {alert.source_database}
</AlertCard>
```

**Six months later**, a backend developer adding a new alert type decides
`explanation` is a vague name and renames it to `message`. Every Python test
passes — `decision_engine.py` is internally consistent, the rule tests assert on
the `Alert` object's attributes, nothing in the backend breaks.

```
   BACKEND                          NETWORK              FRONTEND
   ───────                          ───────              ────────
   Alert(message=...)   ──JSON──►  {"message": ...}  ──► alert.explanation
   ✓ all tests pass                                       ▲
                                                          │
                                                    what happens here?
```

---

## 2. ❌ My answer: "the frontend will throw an error"

**Wrong — and this is the most important fact in the chapter.**

> **JavaScript does not throw on a missing property. It returns `undefined`.**

```javascript
const alert = { message: "Warfarin + Aspirin: increased bleeding risk" };

alert.explanation        // → undefined     (no error, no warning)
```

Contrast with Python, where the same mistake is loud (this is the `KeyError`
from 11.1):

```
  Python:      payload["explanation"]   →  KeyError        ✗ LOUD
  JavaScript:  alert.explanation        →  undefined       ✗ SILENT
```

Python's `[]` access is a **demand** — the key must exist. JavaScript's `.`
access is a **question**, and "nothing there" is an acceptable answer.

### What React does with `undefined`

```jsx
<p>{undefined}</p>     →     <p></p>
```

Rendered as **nothing at all.** No error boundary, no red screen, no console
warning. The deploy produces:

```
  ┌────────────────────────────────────────┐
  │  [ HIGH ]                              │  ← severity badge, still red
  │                                        │  ← explanation: EMPTY
  │  DrugBank v5.1                         │  ← source, still there
  └────────────────────────────────────────┘
```

The card renders. Right colour. Has a source. Simply doesn't say what the
danger *is*.

---

## 3. Why this failure is worse than 11.1–11.3

```
  11.1  bad payload      → 422, names the field           LOUD
  11.2  Neo4j down       → CHECK_UNAVAILABLE on screen    LOUD
  11.3  low confidence   → routed to human review         LOUD
  11.4  renamed field    → blank space on a red card      SILENT
```

Those three were failures somebody **designed a loud response for**. This one
has no response, because **nothing anywhere considers it a failure**:

- The backend is correct.
- The frontend is correct.
- The JSON is valid.
- Every test passes on both sides.

> **The bug lives in the gap between two correct systems — in an agreement that
> was never written down anywhere.**

### The clinical reading

A clinician sees a HIGH severity alert with no stated reason.

| | Outcome |
|---|---|
| Best case | confused, loses 30 seconds they don't have |
| Worse | concludes the system is glitchy, starts dismissing alerts |
| Worst | acts on the severity badge alone, with no idea which drug pair triggered it |

What was violated has a name: an **implicit contract**. The frontend depended on
`explanation` existing. The backend never promised it would. Nothing enforced
the dependency, so it held right up until it didn't.

## 4. Making the promise explicit

```python
from pydantic import BaseModel
from typing import Literal

class AlertResponse(BaseModel):
    risk_type:       str
    severity:        Literal["LOW", "MODERATE", "HIGH", "CRITICAL", "SYSTEM"]
    explanation:     str
    evidence:        str
    source_database: str

@app.post("/api/analyze", response_model=AlertResponse)
def analyze(patient: Patient) -> AlertResponse:
    ...
```

Same `BaseModel` from 11.1, pointed the other direction:

```
        INBOUND                              OUTBOUND
   ┌──────────────┐                    ┌──────────────────┐
   │   Patient    │  ── rules ──►      │  AlertResponse   │
   │  validates   │                    │   guarantees     │
   │  what comes  │                    │   what goes      │
   │      IN      │                    │      OUT         │
   └──────────────┘                    └──────────────────┘
     Ch 11.1                              Ch 11.4
```

**Verified — the rename is now caught in the backend, before any JSON is sent:**

```
AlertResponse(risk_type="X", severity="HIGH", message="renamed!", ...)
  ('explanation',) -> missing: Field required
```

## 5. Why `Literal` and not `str`

The frontend maps severity to colour with a lookup table:

```jsx
const sevColor = (severity) => ({
  LOW:      "grey",
  MODERATE: "amber",
  HIGH:     "red",
  CRITICAL: "red",
  SYSTEM:   "blue",
}[severity]);
```

With `severity: str`, a developer adding a rule can write `"Severe"`, `"high"`,
`"URGENT"`, or `"HIGH "` with a trailing space. Pydantic accepts all of them —
they are valid strings.

**Verified — the JavaScript lookup on each:**

```
  sevColor('HIGH'  ) -> red
  sevColor('Severe') -> None      (JS: undefined)
  sevColor('HIGH ' ) -> None      (JS: undefined)
```

```jsx
<Badge color={undefined}>Severe</Badge>
```

The badge renders with **no colour**. On a screen where colour *is* the severity
signal, a genuinely critical alert appears in default grey — indistinguishable
from the lowest-priority item on the page.

```
  severity="HIGH"      →  sevColor → "red"       →  ┃■┃ HIGH      ← reads as danger
  severity="Severe"    →  sevColor → undefined   →  ┃ ┃ Severe    ← reads as routine
                                        ▲
                                        └── the more urgent alert
                                            is the less visible one
```

**An inverted safety signal, produced by a developer typing a synonym.** And
`"HIGH "` with a trailing space fails identically — it looks correct in the logs
and still misses the lookup.

**Verified — `Literal` makes every one impossible:**

```
  'Severe'   -> rejected: literal_error
  'high'     -> rejected: literal_error
  'HIGH '    -> rejected: literal_error
  'URGENT'   -> rejected: literal_error
```

The `Alert` cannot be constructed at all. The bad value never becomes JSON.

## 6. Who the annotation actually protects

This is the conceptual heart of 11.4.

In 11.1, `age: int` protected **this system** from a bad EHR export — data
arriving from outside, possibly broken.

Here, nothing external is involved. `severity` is produced by your own code, in
your own repo, by a developer on your own team.

```
  Ch 11.1  Patient        protects US from THEM     (untrusted input)
  Ch 11.4  AlertResponse  protects THEM from US     (our own mistakes)
```

`AlertResponse` exists to protect the **consumer** — the React frontend, a
hospital's integration team, a future you.

> **Validation** asks *"is this data acceptable?"*
> **A contract** asserts *"this shape will not change without someone noticing."*

Note the enforcement direction: nobody can quietly rename `explanation` or
invent `"Severe"`, because the contract fails **first** — in CI, in the backend,
before deploy.

### Free documentation

FastAPI generates an OpenAPI schema from `response_model` automatically, served
at `/docs`. The frontend team reads the **actual contract** instead of guessing
from a sample response someone pasted in Slack. The promise becomes
documentation without anyone maintaining documentation.

## 7. Two gotchas worth knowing now

### Extra fields are silently dropped by default

```
  Loose(a=1, b=2)   ->  {'a': 1}          ← b vanished, no warning
```

This is why the rename in §4 surfaced as *"explanation: Field required"* rather
than *"message: unexpected field"*. Pydantic ignored `message` entirely and then
complained about what was missing. To catch the extra field too:

```python
from pydantic import ConfigDict

class Strict(BaseModel):
    model_config = ConfigDict(extra="forbid")
    a: int
```

```
  Strict(a=1, b=2)  ->  extra_forbidden
```

Use `extra="forbid"` on request models to catch typos in incoming payloads
(`{"eGFR": 45}` vs `{"egfr": 45}`). On response models the required-field check
already does the work.

### The envelope carries the degraded state from 11.2

A single alert isn't the whole response. The endpoint must also convey *which
checks ran*:

```python
class AnalysisResponse(BaseModel):
    patient_id:       str
    alerts:           List[AlertResponse] = []
    checks_completed: List[str] = []
    checks_failed:    List[str] = []
```

**Verified output with Neo4j down:**

```json
{
  "patient_id": "P001",
  "alerts": [
    {
      "risk_type": "DRUG_INTERACTION",
      "severity": "HIGH",
      "explanation": "Warfarin + Aspirin: increased bleeding risk",
      "evidence": "DrugBank DDI record",
      "source_database": "DrugBank v5.1"
    },
    {
      "risk_type": "CHECK_UNAVAILABLE",
      "severity": "SYSTEM",
      "explanation": "Interaction screening could not be completed.",
      "evidence": "",
      "source_database": "unavailable"
    }
  ],
  "checks_completed": ["renal_risk_rule", "polypharmacy_rule"],
  "checks_failed": ["ddi_rule"]
}
```

`checks_failed` is the contract-level version of 11.2's principle. **An empty
`alerts` list is ambiguous** — it could mean "patient is fine" or "nothing ran."
`checks_completed` removes the ambiguity. The frontend can now render "3 of 4
checks completed" instead of an unqualified clean bill of health.

## 8. Runnable file

```python
"""11.4 — the response contract.
   Catches renamed fields, synonym severities, and ambiguous empty results."""

from pydantic import BaseModel, ValidationError, ConfigDict
from typing import Literal, List
import json


class AlertResponse(BaseModel):
    model_config = ConfigDict(extra="forbid")

    risk_type:       str
    severity:        Literal["LOW", "MODERATE", "HIGH", "CRITICAL", "SYSTEM"]
    explanation:     str
    evidence:        str
    source_database: str


class AnalysisResponse(BaseModel):
    patient_id:       str
    alerts:           List[AlertResponse] = []
    checks_completed: List[str] = []
    checks_failed:    List[str] = []


# what the React frontend does with severity
SEV_COLOR = {"LOW": "grey", "MODERATE": "amber",
             "HIGH": "red", "CRITICAL": "red", "SYSTEM": "blue"}


if __name__ == "__main__":
    ok = AlertResponse(
        risk_type="DRUG_INTERACTION", severity="HIGH",
        explanation="Warfarin + Aspirin: increased bleeding risk",
        evidence="DrugBank DDI record", source_database="DrugBank v5.1")

    print("--- the rename, caught before it ships ---")
    try:
        AlertResponse(risk_type="X", severity="HIGH", message="renamed!",
                      evidence="e", source_database="s")
    except ValidationError as e:
        for err in e.errors():
            print(f"  {err['loc']} -> {err['type']}: {err['msg']}")

    print("\n--- synonym severities, caught before they ship ---")
    for bad in ["Severe", "high", "HIGH ", "URGENT"]:
        try:
            AlertResponse(risk_type="X", severity=bad, explanation="e",
                          evidence="e", source_database="s")
            print(f"  {bad!r:10} -> ACCEPTED (would render colourless!)")
        except ValidationError as e:
            print(f"  {bad!r:10} -> rejected: {e.errors()[0]['type']}"
                  f"   (JS would have got {SEV_COLOR.get(bad)})")

    print("\n--- degraded response: honest about what did NOT run ---")
    degraded = AnalysisResponse(
        patient_id="P001",
        alerts=[ok, AlertResponse(
            risk_type="CHECK_UNAVAILABLE", severity="SYSTEM",
            explanation="Interaction screening could not be completed.",
            evidence="", source_database="unavailable")],
        checks_completed=["renal_risk_rule", "polypharmacy_rule"],
        checks_failed=["ddi_rule"])
    print(json.dumps(degraded.model_dump(), indent=2))
```

## 9. Never forget — carry these forward

1. **JavaScript returns `undefined` for a missing property; Python raises
   `KeyError`.** The same mistake is loud in one language and silent in the
   other. Every backend↔frontend boundary crosses that asymmetry.

2. **React renders `undefined` as nothing.** No error, no warning — just an
   empty element where information should be.

3. **The worst bugs live in the gap between two correct systems.** Both sides
   pass their own tests; the agreement between them was never written down.

4. **Validation protects you from them. A contract protects them from you.**
   Same `BaseModel`, opposite direction, different purpose.

5. **`Literal` for any value the consumer switches on.** A free-form `str` in a
   colour/icon/routing key is an inverted-safety-signal waiting to happen —
   `"Severe"` renders as calm grey.

6. **Trailing whitespace and casing are real bugs.** `"HIGH "` looks correct in
   every log and fails every lookup.

7. **An empty result list is ambiguous.** "Nothing wrong" and "nothing ran" must
   be distinguishable in the payload itself — hence `checks_completed` /
   `checks_failed`.

8. **`extra="forbid"` catches typo'd field names** that Pydantic would otherwise
   drop in silence.

**Chapter 11's complete through-line:**

```
  11.1  bad data must fail LOUDLY at the boundary
  11.2  a broken dependency must fail LOUDLY at the rule
  11.3  an uncertain model must fail LOUDLY at the gate
  11.4  a changed shape must fail LOUDLY at the contract
        └── one principle, four layers:
            never let "I don't know" be rendered as an answer
```
