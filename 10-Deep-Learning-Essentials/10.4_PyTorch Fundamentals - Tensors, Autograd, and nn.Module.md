## 1. Why This Exists — The Bridge From Keras to PyTorch

Keras (Chapter 9.7) hides almost everything. Writing `model.fit(X, y)` silently runs forward pass → loss → backpropagation → weight update, in a loop, automatically. That's excellent for speed, but it means backpropagation was only ever seen in *theory* (the chain rule derivation in 9.5) — Keras never required writing it out.

**PyTorch does the opposite.** It hands over the raw pieces — tensors, gradients, layers — and the training loop is written by hand. Nothing conceptually new is being taught here — it's the same forward pass, the same backpropagation, the same `w = w − η·∂L/∂w` from Chapter 9. Only the *tool* changes. This matters specifically because PyTorch — not Keras — is the framework the real GNN drug-ranking research was built in.

| | Keras (9.7) | PyTorch (10.4) |
|---|---|---|
| Philosophy | Describe what you want, framework handles the rest | Give the building blocks, assemble the loop yourself |
| Training loop | Hidden inside `.fit()` | Written explicitly |
| Best for | Fast prototyping | Research, custom architectures (like GNNs) |
| Used in the GNN research? | No | Yes — entirely |

## 2. Tensors — the Basic Unit of Everything

A **tensor** is PyTorch's version of a NumPy array — a container for numbers, of any dimensionality:

```python
import torch

scalar = torch.tensor(5.0)                       # 0-D: a single number
vector = torch.tensor([1.0, 2.0, 3.0])            # 1-D: one applicant's features
matrix = torch.tensor([[1.0, 2.0], [3.0, 4.0]])   # 2-D: a batch of applicants
```

Tensors behave almost identically to NumPy arrays — same slicing, same broadcasting, same arithmetic:

```python
x = torch.tensor([1.0, 2.0, 3.0])
y = torch.tensor([4.0, 5.0, 6.0])

print(x + y)      # tensor([5., 7., 9.])
print(x * y)       # tensor([4., 10., 18.])
print(x @ y)        # dot product: 32.0
print(x.shape)       # torch.Size([3])
```

**The one thing NumPy arrays don't have, that makes tensors special: `requires_grad`.**

```python
w = torch.tensor(2.0, requires_grad=True)   # "track every operation done to this number"
```

This single flag is the seed of everything else in this chapter. It tells PyTorch: *"remember every mathematical operation applied to `w`, so that later I can ask you: if I nudge `w` slightly, how much does the final loss change?"* — which is exactly `∂Loss/∂w`, the thing gradient descent needs.

## 3. Autograd — Automatic Differentiation

Chapter 9.5 manually derived `∂L/∂w1 = (ŷ − y) × wa × ReLU′(z1) × x1` by hand, applying the chain rule. That was valuable for *understanding* backpropagation, but doing that by hand for millions of weights is impossible. **Autograd is PyTorch's engine that does that chain-rule bookkeeping automatically**, for every weight, no matter how deep the network.

Here's the exact mechanism, with a tiny worked example matching the 9.4/9.5 derivations:

```python
import torch

w = torch.tensor(0.5, requires_grad=True)   # weight
b = torch.tensor(0.1, requires_grad=True)   # bias
x = torch.tensor(2.0)                        # input (scaled income) — no grad needed, it's fixed data
y_true = torch.tensor(1.0)                   # true label

z = w * x + b                     # weighted sum, z = wx + b
y_pred = torch.sigmoid(z)         # activation

loss = -(y_true * torch.log(y_pred) + (1 - y_true) * torch.log(1 - y_pred))  # BCE, from 9.4

print("Loss:", loss.item())

loss.backward()    # <-- autograd. Computes ∂loss/∂w and ∂loss/∂b automatically.

print("∂Loss/∂w:", w.grad.item())
print("∂Loss/∂b:", b.grad.item())
```

**What `loss.backward()` actually did:** every operation (`w*x`, `+b`, `sigmoid`, `log`, etc.) was silently recorded into a **computational graph** as it happened during the forward pass. Calling `.backward()` walks that graph **backward**, applying the chain rule at each recorded step — precisely the "blame flows backward through the same weights that carried data forward" idea from 9.5. It computes `∂L/∂w` and `∂L/∂b` and stores them in `w.grad` and `b.grad`. No derivative was written by hand — autograd derived it from the recorded operations.

**Verifying it matches the hand-derivation from 9.4:** you proved `∂L/∂z = ŷ − y`.

```python
print("Manual ŷ - y:", (y_pred - y_true).item())
```

`w.grad` will equal `(ŷ − y) × x` — exactly the chain rule term from the 9.5 derivation (`∂L/∂w1 = (ŷ−y) × wa × ReLU′(z1) × x1`, simplified here to a single neuron with no upstream layer). Autograd isn't magic — it's mechanically performing the same calculus done by hand earlier, just automatically and for arbitrarily many weights.

**A critical gotcha — gradients accumulate by default:**

```python
w.grad.zero_()   # must clear gradients before the next .backward() call
```

If `.backward()` is called twice without clearing, PyTorch **adds** the new gradients to the old ones instead of replacing them — silently corrupting training. This is exactly why `optimizer.zero_grad()` exists (already seen in 9.6/9.7) — it clears every weight's `.grad` before each new backward pass.

## 4. `nn.Module` — Organizing Weights Into an Actual Network

Manually tracking `w`, `b` as separate variables is fine for one neuron, hopeless for a real network. `nn.Module` bundles many weights (and the forward-pass logic connecting them) into one clean object — the direct PyTorch equivalent of Keras' `Sequential` + `Dense`.

```python
import torch.nn as nn

class LoanNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = nn.Linear(5, 32)   # 5 input features -> 32 juniors (matching 9.8's architecture)
        self.layer2 = nn.Linear(32, 16)  # 32 -> 16
        self.layer3 = nn.Linear(16, 1)   # 16 -> 1 output
        self.relu = nn.ReLU()
        self.sigmoid = nn.Sigmoid()

    def forward(self, x):
        x = self.relu(self.layer1(x))    # ground floor juniors
        x = self.relu(self.layer2(x))    # first floor juniors
        x = self.sigmoid(self.layer3(x)) # senior officer's final call
        return x

model = LoanNet()
```

This is exactly the 9.8 architecture (32 → 16 → 1 funnel, ReLU hidden, Sigmoid output) — the same network, just written explicitly instead of Keras' `Sequential([...])` shorthand. `nn.Linear(5, 32)` is PyTorch's `Dense(32)` — it internally holds a `5×32` weight matrix and a 32-length bias vector, both automatically `requires_grad=True`.

`model.parameters()` gives every weight and bias across all three layers, bundled together — this is what gets handed to the optimizer:

```python
import torch.optim as optim

optimizer = optim.Adam(model.parameters(), lr=0.001, weight_decay=1e-5)  # same line from 9.6/10.1
```

## 5. The Full Manual Training Loop

This is the payoff — the three lines memorized in 9.6/9.7 (`zero_grad`, `backward`, `step`) now make complete sense inside a real loop:

```python
import torch
import torch.nn as nn
import torch.optim as optim

model = LoanNet()
criterion = nn.BCELoss()                                                  # same BCE from 9.4
optimizer = optim.Adam(model.parameters(), lr=0.001, weight_decay=1e-5)   # Adam + L2, from 9.6/10.1

epochs = 100

for epoch in range(epochs):
    # ---- FORWARD PASS ----
    y_pred = model(X_train)              # runs the forward() method above
    loss = criterion(y_pred, y_train)     # BCE loss between prediction and truth

    # ---- BACKWARD PASS ----
    optimizer.zero_grad()   # clear old gradients (else they'd accumulate — see Section 3)
    loss.backward()          # autograd computes ∂Loss/∂w for EVERY weight in the model
    optimizer.step()         # apply w = w − η·(Adam's formula using those gradients)

    if epoch % 10 == 0:
        print(f"Epoch {epoch}, Loss: {loss.item():.4f}")
```

Compare this, line for line, to what Keras did invisibly inside `model.fit(X_train, y_train, epochs=100)`:

| Keras (hidden inside `.fit()`) | PyTorch (written by hand) |
|---|---|
| Forward pass | `y_pred = model(X_train)` |
| Compute loss | `loss = criterion(y_pred, y_train)` |
| Clear old gradients | `optimizer.zero_grad()` |
| Backpropagation (the 9.5 chain rule) | `loss.backward()` |
| Apply the weight update formula (9.6) | `optimizer.step()` |

## 6. Adding Dropout, BatchNorm, Early Stopping, and Embeddings — All of Chapter 10 in One Place

```python
class FullNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = nn.Linear(5, 100)
        self.bn1 = nn.BatchNorm1d(100)      # 10.2
        self.dropout = nn.Dropout(0.5)       # 10.1
        self.layer2 = nn.Linear(100, 1)
        self.relu = nn.ReLU()
        self.sigmoid = nn.Sigmoid()

    def forward(self, x):
        x = self.layer1(x)
        x = self.bn1(x)          # normalize BEFORE activation (10.2 convention)
        x = self.relu(x)
        x = self.dropout(x)      # then randomly silence neurons (10.1)
        x = self.sigmoid(self.layer2(x))
        return x
```

`model.train()` / `model.eval()` switches Dropout and BatchNorm's behaviour together, exactly as discussed in 10.1 and 10.2 — one switch, both layers respond correctly.

Early stopping isn't a built-in PyTorch feature (unlike Keras' `EarlyStopping` callback) — `val_loss` is tracked manually, inside the loop:

```python
best_val_loss = float('inf')
patience_counter = 0
patience = 10

for epoch in range(500):
    model.train()
    y_pred = model(X_train)
    loss = criterion(y_pred, y_train)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()

    model.eval()
    with torch.no_grad():              # don't track gradients during evaluation — saves memory/time
        val_pred = model(X_val)
        val_loss = criterion(val_pred, y_val)

    if val_loss < best_val_loss:
        best_val_loss = val_loss
        patience_counter = 0
        torch.save(model.state_dict(), 'best_model.pt')   # save best weights, like restore_best_weights=True
    else:
        patience_counter += 1
        if patience_counter >= patience:
            print(f"Early stopping at epoch {epoch}")
            break

model.load_state_dict(torch.load('best_model.pt'))   # restore best weights
```

`with torch.no_grad():` tells autograd "don't bother recording operations here, `.backward()` will never be called on this." It saves memory and computation during evaluation, since there's no training happening on the validation set.

## 7. Merits and Demerits

**Merits:**
- Full transparency and control over the training loop — essential for custom architectures like GNNs, where the "layer" (e.g. `HANConv`) doesn't exist as a pre-built Keras layer
- Easier to debug — any intermediate tensor mid-forward-pass can simply be printed
- Dominant framework in research (and specifically in PyTorch Geometric, the library the GNN research uses)

**Demerits:**
- More boilerplate — the training loop, early stopping, etc. must be written by hand
- Easier to introduce bugs (forgetting `zero_grad()`, forgetting `.eval()`) since nothing is hidden or protected the way Keras protects it
- Steeper learning curve for beginners — exactly why Chapter 9 taught Keras first
