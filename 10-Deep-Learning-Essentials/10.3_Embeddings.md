## 1. The Problem — What One-Hot Encoding Can't Do

Chapter 2 introduced **One-Hot Encoding**: each category gets its own binary column, avoiding the false ordering that Label Encoding would introduce. For `employment_type` with categories {Salaried, Self-Employed, Business Owner}:

```
Salaried       → [1, 0, 0]
Self-Employed  → [0, 1, 0]
Business Owner → [0, 0, 1]
```

This works fine for a handful of categories. But consider the GNN research: **thousands of unique drugs, patients, and genes.** One-hot encoding a "drug" feature with 5,000 unique drugs means every drug becomes a 5,000-dimensional vector that's almost entirely zeros, with a single 1. Three problems fall out immediately:

1. **Massive, wasteful dimensionality** — 5,000 columns for what should be a compact idea.
2. **Zero notion of similarity.** The one-hot vectors for "Aspirin" and "Ibuprofen" (both NSAIDs, chemically similar) are exactly as different from each other as "Aspirin" and "Chemotherapy Drug X" (completely unrelated) — the mathematical distance between any two one-hot vectors is identical. There's no way to express "Aspirin and Ibuprofen are more alike than Aspirin and Chemo Drug X," even though that's obviously true and useful information.
3. **Doesn't scale.** Every new drug added grows the entire feature space by one more dimension.

**Ravi analogy:** imagine 5,000 different `employment_type` categories instead of 3 (every possible job title). One-hot encoding means each junior officer looks at a 5,000-length list of zeros with a single 1 somewhere in it, with no way of knowing that "Software Engineer" and "Data Scientist" are similar occupations with similar risk profiles, while "Software Engineer" and "Fisherman" are very different. Every job title looks equally unrelated to every other job title.

## 2. The Idea — A Dense, Learned Vector Instead of a Sparse, Fixed One

Instead of a 5,000-dimensional, mostly-zero vector, give each entity (drug, patient, gene, job title — anything) a **small, dense vector of real numbers**, say 32 or 64 numbers, all of which can be non-zero:

```
Aspirin        → [0.82, -0.14, 0.55, ..., 0.09]   (32 numbers)
Ibuprofen      → [0.79, -0.11, 0.51, ..., 0.12]   (32 numbers — CLOSE to Aspirin's vector)
Chemo Drug X   → [-0.63, 0.91, -0.22, ..., -0.77] (32 numbers — FAR from Aspirin's vector)
```

This is an **embedding** — a dense, lower-dimensional, *learned* representation of an entity. The crucial word is **learned**. Nobody hand-designs these 32 numbers. They start random and get updated by gradient descent, exactly like every other weight in the network — `w = w − η·∂Loss/∂w` — except here, the "weight" being updated is literally the vector representing "Aspirin."

**Why this fixes all three problems from Section 1:**

1. Dimensionality is fixed and small (32 or 64) regardless of how many drugs exist — 5,000 drugs or 500,000, still 32 numbers each.
2. Similarity emerges naturally. If Aspirin and Ibuprofen tend to behave similarly with respect to the task the network is trained on (e.g., predicting patient outcomes), gradient descent will naturally push their embedding vectors close together — because doing so reduces the loss. This closeness can be measured directly with cosine similarity or Euclidean distance.
3. Adding a new drug just means adding one more row to a lookup table — no restructuring of the whole feature space.

---

## 3. The Mechanism — A Lookup Table With Learnable Rows

An embedding layer is conceptually a big table:

```
Row 0 (Aspirin)      → [0.82, -0.14, 0.55, ...]
Row 1 (Ibuprofen)    → [0.79, -0.11, 0.51, ...]
Row 2 (Chemo Drug X) → [-0.63, 0.91, -0.22, ...]
...
Row 4999 (last drug) → [...]
```

When "Aspirin" (drug ID = 0) flows into the network, the embedding layer literally **looks up row 0** and returns that vector — no matrix multiplication needed, just indexing. That vector is used downstream, and when backpropagation runs, **only row 0 gets updated** (the row for whichever drug was in that training example) — every other row is untouched on that step, since it played no part in that prediction.

This is subtly different from every other weight seen so far. In a normal `Dense` layer, every weight participates in every forward pass. In an embedding table, only the rows corresponding to entities actually present in the current batch get touched.

## 4. Code

**PyTorch:**

```python
import torch
import torch.nn as nn

num_drugs = 5000
embedding_dim = 32   # hyperparameter — how many numbers represent each drug

drug_embedding = nn.Embedding(num_embeddings=num_drugs, embedding_dim=embedding_dim)

drug_id = torch.tensor([0, 1, 2])   # a small batch: Aspirin, Ibuprofen, Chemo Drug X
vectors = drug_embedding(drug_id)   # shape: [3, 32] — one 32-length vector per drug

print(vectors.shape)   # torch.Size([3, 32])
```

`drug_embedding` internally holds a `5000 × 32` matrix, initially random. As the whole network trains on a real prediction task, gradient descent nudges these rows around, and semantically similar drugs end up nearby in this 32-dimensional space — purely as a side effect of being trained on a task where "behaving similarly" is rewarded.

**Keras:**

```python
from tensorflow.keras.layers import Embedding

drug_embedding_layer = Embedding(input_dim=5000, output_dim=32)
```

### 4.1 Measuring Learned Similarity

```python
import torch.nn.functional as F

aspirin_vec = drug_embedding(torch.tensor([0]))
ibuprofen_vec = drug_embedding(torch.tensor([1]))
chemo_vec = drug_embedding(torch.tensor([2]))

sim_aspirin_ibuprofen = F.cosine_similarity(aspirin_vec, ibuprofen_vec)
sim_aspirin_chemo = F.cosine_similarity(aspirin_vec, chemo_vec)

# After real training on real data, you'd expect:
# sim_aspirin_ibuprofen  → closer to 1 (similar behavior/effect)
# sim_aspirin_chemo      → closer to 0 or negative (dissimilar)
```

Right after random initialization these similarities are meaningless — it's only *after* training on the actual task that the geometry becomes informative.

## 5. Direct Connection to the GNN Research

This is exactly what happens with `HeteroData` in the drug-ranking project: **every patient, drug, gene, and disease node starts as an embedding row** — a learned vector, not necessarily a raw feature. The entire point of `HANConv` and message passing (Chapter 12) is to **update these embeddings** by having nodes exchange information with their graph neighbors, so a drug's final embedding reflects not just "what drug is this" but "what does this drug tend to do, based on which patients/genes/diseases it connects to." Chapter 10.3 is the *before* picture — a static, per-entity learned vector. Chapter 12 is the *after* picture — embeddings refined by graph structure.

## 6. How Is This Different From PCA (Chapter 3-ish Territory)?

Worth being precise, since the two can look similar on the surface:

| | PCA / dimensionality reduction | Embeddings |
|---|---|---|
| Learned how? | Unsupervised — purely from variance in existing features | Supervised — learned end-to-end via the actual task's loss |
| Input | Requires existing numeric features to compress | Requires only a category ID (e.g., drug #347) — no features needed at all |
| What it optimizes for | Preserving overall variance | Whatever makes the downstream prediction task work best |
| Can create representations from scratch? | No — needs something to compress | Yes — even a brand-new drug ID with zero known numeric features gets a meaningful vector once trained |

## 7. Merits and Demerits

**Merits:**
- Massive dimensionality reduction vs. one-hot (32 numbers vs. 5,000)
- Captures **semantic similarity** automatically — no one has to hand-define "these drugs are similar"
- Scales to huge vocabularies (word embeddings in NLP handle hundreds of thousands of words this way — a preview of Chapter 13)
- Reusable — embeddings learned for one task sometimes transfer usefully to related tasks (pretrained embeddings)

**Demerits:**
- **Needs enough training data per entity** — a drug appearing only once in the entire dataset gets almost no meaningful gradient signal; its embedding stays close to its random initialization (a "cold start" problem)
- **Uninterpretable dimensions** — dimension #17 of the embedding doesn't mean anything human-readable on its own; only relative distances/directions in the space are meaningful
- Choosing `embedding_dim` is a hyperparameter guess — too small and it can't capture enough nuance, too large and it risks overfitting (echoing the same capacity-vs-overfitting logic from Chapter 10.1)
- Brand-new entities never seen during training (a drug added after deployment) have no learned embedding at all — needs special handling (e.g., a generic "unknown" embedding row)
